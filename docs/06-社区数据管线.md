# 06 · 社区数据管线

> ⚠️ **决策 D2/D3 已作废（见 `docs/09` §5.2 铁律）。**
>
> 原文写的是"利用社区整合的游戏机制数据，**不自行反编译 `sts2.dll`**"。
> 这条决策基于一个当时看起来合理的判断：社区数据能省掉读源码的功夫。
> **实测是错的**，两条硬证据：
>
> 1. **社区库落后至少一个补丁。** 逐字节对拍发现 651 个变量里 **37 个不一致（5.7%）**；
>    v0.110.0 补丁说明证实"说明里的旧值 = 社区库，新值 = 源码"。
> 2. **社区 API 不提供任何版本或日期**（没有 `Last-Modified`、没有 `ETag`），
>    也就是说**没有任何办法确认它是不是最新的**。一个无法确认版本的数据源
>    不能作为数值依据。
>
> 现行规则：**数值与行为都从 `data/decompiled/sts2/` 取；JSON 只提供 id、类名与结构。**
> 本篇其余内容仍然有效 —— 社区数据依然是**对账的基准**与**发现遗漏的线索**
> （"社区库说这张卡有易伤，为什么我没抽出来？"），只是不再提供数值。

这一篇解决一个具体问题：**怎么把社区数据变成对账基准与查漏线索**，而不是把别人的 JSON 直接喂进模拟器。

## 6.1 为什么"直接用"会出事

| 隐患 | 具体后果 |
|---|---|
| **版本漂移** | 游戏处于 EA，更新频繁。社区数据可能对应旧版本，数值已经改了 |
| **覆盖不全** | 社区站点通常优先收录"玩家关心"的内容（卡牌、遗物），边角机制（特定交互、稀有事件分支）常常缺失或含糊 |
| **转写错误** | 反编译产物经过"代码 → 结构化数据 → 站点展示"多次转手，每一步都可能出错 |
| **粒度不匹配** | 社区数据是"展示用"的（卡面上写什么），我们要的是"执行用"的（精确的结算顺序、中间量）。**"造成 8 点伤害"和"什么时候结算易伤加成"是两回事** |
| **许可证不明** | 部分仓库许可标注为 `NOASSERTION`，直接复制可能有问题 |

结论：社区数据是**原料**，不是**成品**。需要一条明确的加工管线。

## 6.2 三类社区资产，三种用法

| 资产 | 内容 | 用法 | 可信度 |
|---|---|---|---|
| **内容数据** | 卡牌/遗物/怪物/遭遇/事件的数值与描述 | 半自动生成我们的内容表（§6.3 的映射） | 中——需逐项校验 |
| **机制知识** | 结算顺序、buff 交互、关键词定义、AI 行为 | 人工转写成规则实现 + 测试用例 | 中——需实测确认 |
| **真机数据** | 状态导出、对局记录、逐步决策 | **对拍验证**（§6.5）+ BC 数据源 | 高——直接来自游戏 |

> 关键认知（**已按 `docs/09` §5.2 更正**）：原文写"前两类可以省掉'读源码'的功夫，
> 但省不掉'搞清楚机制'的功夫"—— 后半句是对的，**前半句是错的**。
>
> 社区数据**不能**提供数值（落后至少一个补丁、且无法确认版本），
> 也**不能**提供机制（它说"这张牌造成 8 点伤害"，但不会说"对方有 3 层易伤、
> 你有 2 点力量时先算哪个"）。它真正的作用是两个：
>
> * **对账**：拿它的描述反查"我是不是漏抽了某个效果"
> * **查漏**：两边条目集合不一致时，说明抽取器有问题
>
> 数值与结算顺序一律回 `data/decompiled/sts2/` 读源码确认。

## 6.3 管线四阶段

```
┌─────────┐   ┌────────────┐   ┌───────────┐   ┌──────────┐   ┌────────┐
│  fetch  │──►│ normalize  │──►│ validate  │──►│  verify  │──►│ freeze │
│ 社区来源 │   │ → 我们的    │   │ 静态检查   │   │ 真机对拍  │   │ 版本锁定│
│         │   │   schema   │   │ linter    │   │ 状态比对  │   │ 内容哈希│
└─────────┘   └────────────┘   └───────────┘   └──────────┘   └────────┘
                                                      │
                                              标记 verified: true/false
```

### fetch

- 优先用**结构化接口**（社区 API / 仓库里的数据文件），而不是抓网页。
- 抓下来的原始数据**原样归档**到 `data/raw/<source>/<version>/`，带抓取时间与来源 URL。
  **理由**：将来对拍失败时，要能回答"是我们解析错了，还是源头就是错的"。
- 记录来源版本号（游戏版本 / 仓库 commit）。

### normalize

把社区 schema 映射到我们的内容表 schema（`docs/02` §2.3）。

**映射表**（字段名待社区数据确认后补全）：

| 我们的字段 | 来源 | 转换 |
|---|---|---|
| `Card.id` | 社区卡牌标识 | 统一成小写下划线命名 |
| `Card.cost` | 社区费用 | 直接映射；注意负数/X 费的特殊编码 |
| `Card.card_type` | 社区类型 | 枚举映射（Attack/Skill/Power/Status/Curse/…） |
| `Card.rarity` | 社区稀有度 | 枚举映射 |
| `Card.target` | 社区目标 | 推断（单体/全体/自身/无目标）——**需规则推断，社区常不显式给出** |
| `Card.effects` | 社区效果描述文本 | ⚠️ **半自动**：文本 → 效果 DSL 需要解析，无法全自动（§6.4） |
| `Card.upgrade` | 升级后数值 | 同上 |
| `Card.text` | 描述文本 | 保留，供文本 embedding（`docs/03` §3.3）与人工核对 |

**核心难点：`effects` 无法全自动映射。** 社区数据里的"效果"通常是给人读的自然语言（"造成 8 点伤害。施加 2 层易伤。"），而我们需要可执行的结构。所以：

1. 写一个**规则解析器**处理高频句式（"造成 N 点伤害"、"获得 N 点格挡"、"施加 N 层 X"、"抽 N 张牌"）——能覆盖 60–80% 的卡。
2. 解析不了的**自动列成待办清单**，人工补写（每张几十秒）。
3. 全部解析结果都要过 linter 与单卡测试。

> 不要试图写一个通用 NLP 解析器。**按句式模板匹配 + 人工兜底**是最快的路。

### 来源优先级与去重（踩过三次，方向各不相同）

真实下载会同时拿到**三类来源**，规则必须写死，否则一定出事：

| 来源 | 语言 | 角色 |
|---|---|---|
| 裸端点 `data/raw/spire-codex/repo/<name>.json` | **英文** | **权威**（16 个数据集都能从 `/api/<name>` 取到） |
| 全量导出 `export_zhs.zip` | **中文** | **只补裸端点没有的数据集** |
| 全量导出 `export_eng.zip` | 英文 | 同上（当前磁盘上没有这个文件，manifest 曾引用它） |

**规则：按「数据集」粒度回退** —— 某个数据集有裸端点文件就用它，没有才去 ZIP 里取。
落地在 `tools/import_content.py::collect_buckets`。

⚠️ 三次踩坑，每次都只修了一半：

1. **重复导入**：不加区分地合并所有来源 → 同一份数据读 3 遍
   （实测 encounters 87 条变 **261** 条 = 87×3）。
2. **静默丢失**：改成 `sources = plain if plain else archives` 的**全有或全无** →
   只要裸端点文件存在，ZIP 就整个不读，ZIP 独有的 7 个数据集
   （`enchantments` / `afflictions` / `orbs` / `intents` / `modifiers` /
   `achievements` / `epochs`）被丢掉，**报告里一个字都不提**。
3. **语言串味**：把裸端点文件一律当英文而不看它们的语言目录，会让
   `zhs/cards.json` 与 `eng/cards.json` **合并**。

两个附属坑：

- **ZIP 里没有语言目录**：`export_zhs.zip` 的成员名就是 `cards.json`，语言只能从
  **归档文件名**推（`language_of_archive`）。不看文件名的话两个语言包会因为
  都落到 `unknown` 而被合并 —— 重复导入又回来了。
- **主键字段名不统一**：`cards` 用 `cid`、`monsters`/`encounters` 用 `eid`、
  其余才叫 `id`。一律用 `record["id"]` 查重会得到 `id唯一=1`（全是 `None`）
  这种"零重复"的**假象**。

**语言之所以是硬约束**：卡牌效果解析器吃的是**英文**描述（`Deal 6 damage.`），
拿中文（`造成6点伤害。`）去套英文句式模板会一条都解不出来 —— 而且不报错。
所以英文裸端点的优先级高于中文导出包，不是"随手挑一份"。

**审计工具**：`tools/audit_data.py` —— 按主键/名字查重、raw 与归一化结果逐数据集
对账、按磁盘实况重建 manifest，并把**源码抽取结果与社区库对账**（HP 逐条比对
114 条，零分歧）。跑 `python tools/audit_data.py --check` 给 CI 用。

### validate（静态检查）

| 检查 | 抓什么 |
|---|---|
| 引用完整性 | 每个 `effect` 引用的 power / keyword / card id 都存在 |
| 数值范围 | 费用 ∈ [-2, 5]、伤害 ∈ [0, 999]，越界报警（很可能是解析错误） |
| 枚举合法性 | 类型/稀有度/目标都在已知枚举内 |
| 结构完整性 | 每张卡都有 id / 费用 / 类型 / 至少一个 effect |
| 覆盖率报告 | 卡池/怪物/遗物/事件的收录比例；哪些还缺 |
| 差异报告 | 与上一版本的 diff：哪些数值变了（游戏更新的信号） |

**差异报告特别有用**：游戏每周更新后，`diff` 就是"这次改了哪些卡"的清单，直接决定要不要重训。

### verify（真机对拍）

这是**唯一能证明**内容表正确的手段，见 §6.5。

### freeze（版本锁定）

```
data/content/
├─ v0.105.0/
│  ├─ cards.ron  relics.ron  monsters.ron  events.ron
│  ├─ manifest.json    # 来源 URL/commit、抓取时间、内容哈希、verified 统计
│  └─ DIFF.md          # 与上一版本的差异
└─ current -> v0.105.0
```

- 每个实验都记录用了哪个内容版本 → 结果可追溯。
- `verified` 字段：每张卡/每个怪物标记是否通过了真机对拍。**训练时可选只使用 verified 的子集。**

## 6.4 机制知识：三种来源，按可信度排序

| 来源 | 能回答什么 | 不能回答什么 |
|---|---|---|
| 社区数据（结构化） | 数值、费用、稀有度、描述 | 结算顺序、交互、边角情况 |
| 社区机制文档/wiki | 关键词定义、buff 交互、常见机制说明 | 精确的实现细节、AI 行为权重 |
| **真机实测** | 一切 | 慢、需要人工设计实验 |

**工作流建议**：对每个机制问题，先查文档 → 形成假设 → 写一个最小对拍实验验证 → 通过后写成单元测试固化。

**必须实测确认的高风险机制**（这些错了会导致系统性偏差）：

- 伤害结算顺序（力量 → 易伤 → 虚弱 → 格挡 → 减免）
- 多个 buff 的叠加与衰减时机（回合开始/结束、谁先谁后）
- 洗牌时机（弃牌堆何时洗回抽牌堆、洗牌用哪条 RNG 流）
- 死亡的结算时机（同回合多个敌人死亡、死亡触发效果）
- 卡牌打出后的去向（弃牌/消耗/回手）与触发顺序
- 怪物 AI 的选招逻辑（权重？序列？条件？）

> 这些**每一条**都应该有一个对应的单元测试。它们不是"细节"，它们是模拟器与真机偏差的主要来源。

## 6.5 真机对拍（管线的验收环节）

```
输入：真机导出的一局记录  (种子, 动作序列, 逐步状态快照)
过程：在模拟器里 replay(种子, 动作序列)
输出：逐帧比对，报告第一处不一致的位置
```

**比对字段**：HP、格挡、能量、各牌堆内容、buff 层数、金币、遗物状态。

对拍失败时的诊断路径：

1. 定位第一处偏差 → 看是哪个动作
2. 该动作涉及的卡/怪/机制 → 检查对应实现
3. 修正 → 加单元测试 → 重跑对拍

**对拍数据的来源**：社区状态导出 mod（只读模式，`docs/05` 待确认 #4）、人工录制 10–20 局。

> **10–20 局对拍就能抓出大部分机制错误。** 这是整个项目里单位时间收益最高的验证手段，M0 阶段就要做。

## 6.6 反模式（明确不要做）

| 反模式 | 为什么不行 |
|---|---|
| 把社区 JSON 直接转成 tensor 喂模型 | 粒度不对（展示用 vs 执行用），且无法验证 |
| 用社区的 tier list / 评分当 reward | 那是人类的启发式偏好，不是游戏的真实回报，会把模型带偏 |
| 假设社区数据是完整的 | 覆盖率报告会告诉你缺什么；缺的部分要显式标记 |
| 追最新版本的数据 | 版本要**锁定**，让模型、数据、游戏三者版本一致；升级是显式动作 |
| 只对拍"看起来复杂"的卡 | 简单卡也会错（费用、升级数值），全量对拍 |
| 把解析器写复杂 | 模板匹配 + 人工兜底，先覆盖 80% |

## 6.7 更新流程（游戏每次更新后）

```
1. 拉取新版社区数据
2. 跑 validate → 看 DIFF.md
3. 若差异为空 → 仅更新版本号，无需重训
4. 若有差异 → 人工确认改动 → 更新内容表 → 跑单卡测试
5. 跑真机对拍 → 标记 verified
6. 评估旧模型在新内容表上的表现 → 决定是否需要微调
```

把这条流程脚本化（一条命令跑完 1–5），否则每次更新都会变成一周的体力活。

### 真机桥接：STS2MCP

| 项 | 值 |
|---|---|
| 仓库 | `Gennadiyev/STS2MCP`（C#，488★，MIT） |
| 能力 | **双向读写**：读状态 + 注入动作（`play_card` / `end_turn` / `select_card_reward` / `choose_map_node` / `shop_purchase` / `choose_rest_option` / `choose_event_option` …） |
| 通信 | localhost HTTP REST，默认端口 **15526**，无鉴权；另有可选 MCP over stdio |
| 覆盖界面 | 菜单/选角/战斗(普通|精英|Boss)/手牌选择/奖励/三选一/地图/事件(含 Ancient)/营火/商店/假商人/宝箱/卡牌选择/遗物选择/水晶球/游戏结束 |
| **限制** | 需要跑**完整真实游戏**（Godot 渲染），**无 headless**；每步延迟与批量模式**未确认** |
| 适配版本 | `v0.103.2` |

**⚠️ 高风险点**：它暴露的是**游戏内部状态**，可能含 L3 级未揭示信息（完整抽牌堆顺序、敌人行动队列）。真机路径**必须做字段白名单过滤**（`docs/01` §1.7）。
