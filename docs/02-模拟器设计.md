# 02 · 模拟器设计

目标：一个**没有美术、没有动画、只有规则与运算**的确定性可复现引擎，跑得足够快，且数值与真机对齐。

## 2.1 第一步不是写代码，是选基座

**决策（`docs/05` D8）：不从头写规则引擎。** 已有多个开源 StS2 模拟器（详见 `docs/07` §7.4），M0 的第一件事是逐个评估它们的行为保真度：

```
1. 克隆（本地执行，我方无出网）
2. 跑它们自带的测试，看覆盖率
3. 用我们的真机对拍脚本打分（§2.5）
4. 选保真度最高的作基座
5. 在其上重写 observe() / 动作定义（它们的接口设计是错的，见 docs/07 §7.2）
```

**验收**：选中的引擎能通过 10–20 局真机对拍的 ≥90%；否则退回自建（下方边界）。

## 2.2 MVP 边界（自建时的裁剪线）

游戏现状（`docs/07` §7.6）：**5 个角色、4 张幕地图 / 3 个幕索引、Ascension 0–10**，
EA 起于 2026-03-05，主分支约每月更新、beta 分支每 1–2 周更新。

> ⚠️ **幕的准确说法**（按源码，见 `docs/09` 与 `docs/12` 的"地图与三幕"一节）：一局只走 **3 个幕索引** ——
> 索引 0 是 `Overgrowth`（密林）或 `Underdocks`（暗港）**随机二选一**（暗港需解锁），
> 索引 1 是 `Hive`（蜂巢），索引 2 是 `Glory`（荣耀）；四张地图的参数各不相同
> （房间数 15/15/14/13）。早先文档里"4 幕"的说法容易被读成"一局打四幕"，不准确。

> ⚠️ **下面这段"第一个可跑通的闭环"是立项时的范围草案，保留作历史参考。**
> 实际范围已由 [`docs/13`](13-实施规划与当前缺口.md) 接管：角色/内容按
> **内容准入**（`sts2_sim/eligibility.py`）滚动放行，地图与幕流程按源码复刻，
> 不再是"先 80–120 张卡"这种按数量切的做法。

**做（第一个可跑通的闭环）：**

- **1 个角色**（选机制最直白的；Ironclad 系角色的战斗模型已有公开参考实现，见 `docs/07` §7.1）
- **第 1 幕（Overgrowth）全部** + 第 2 幕部分
- 卡池子集：先 80–120 张
- 怪物子集：15–25 个（含 1–2 精英 + 1 Boss）
- 遗物子集：20–30 个（优先做"改变规则"而非"仅加数值"的）
- 药水：全部基础药水
- 事件：先做 3–5 个，抽象成"选项 → 效果"
- 完整 run 循环：地图 → 房间 → 奖励 → 商店 → 营火 → Boss
- **Ascension 0–10 的难度参数**（数值表，不是逻辑；StS2 的进阶是 11 级）

**注意 StS2 相比 StS1 的新系统，它们不是可选项：**

| 新系统 | 建模影响 |
|---|---|
| **Enchantments**（附魔，限卡牌类型、可叠加） | 卡牌实例需要额外的附魔槽位；观测要包含 |
| **Ancients**（8 个古代 NPC，幕首给遗物/交易） | 属于 Run 层决策节点，需要独立的动作头分支 |
| **Afflictions**（苦难） | 类似诅咒的负面状态，需要进入状态与观测 |
| **Epochs / Stories / Timeline**（解锁进度） | 与对局无关，**排除** |
| **Badges**（局末徽章，25 个） | 与对局无关，**排除** |
| **Regent 的 star 资源 / Necrobinder 的 pets** | 若选这两个角色则必须建模，是选角色时的成本考量 |
| **4 人 co-op** | **明确排除**（`docs/05` 风险 10） |

**不做：** 美术、音效、动画、UI、多人、成就、存档格式兼容、每日挑战。

**为什么先砍这么狠：** 完整模拟器的工程量是 MVP 的 5–10 倍，而端到端跑通的价值在第 1 个角色时就基本拿到了。**先窄后宽。**

## 2.2 数据结构

```rust
struct RunState {
    rng: RngSet,                  // 命名 RNG 流集合，见 §2.4
    hidden: Hidden,               // 禁止进入观测的一切（见 §01）
    seed: u64,                    // 仅用于复现，禁止进入观测
    act: u8, floor: u8,
    map: MapGraph,
    player: PlayerState,
    room: RoomState,
    history: RunHistory,          // 供观测与调试
}

struct PlayerState {
    hp: i32, max_hp: i32, gold: i32,
    deck: Vec<CardInstance>,
    relics: Vec<RelicInstance>,
    potions: [Option<PotionInstance>; 3],
}

enum RoomState {
    Combat(CombatState),
    CardReward { choices: Vec<CardId> },
    Shop { stock: Vec<ShopItem> },
    Rest, Event { id: EventId, options: Vec<EventOption> },
    Treasure, MapChoice, BossReward,
}

struct CombatState {
    player: CombatPlayer,               // hp, block, energy, powers
    enemies: Vec<EnemyState>,           // hp, max_hp, block, powers, intent, move_history
    hand: Vec<CardInstance>,
    draw_pile: Vec<CardInstance>,       // 内部有序；观测层默认只给 bag（见 docs/03 §3.2）
    discard: Vec<CardInstance>, exhaust: Vec<CardInstance>, play_area: Vec<CardInstance>,
    turn: u32, phase: Phase,
}
```

### 三条硬性设计约束

1. **⭐ `restore` 必须保留隐藏 RNG 状态，不得重掷**
   这是 SL 语义的物理基础（`docs/01` §1.3、§1.6 测试 2）。同一节点重开 N 次，必须面对**同一副牌序**。
   如果 restore 顺手重掷了 RNG，agent 会学到"重开可以刷到好牌"，而这条策略在真机上不存在——**整个训练结果作废**。
   实现建议：`snapshot()` 保存完整的 `RngSet`，`restore()` 原样写回；把"重掷"做成一个**显式的、只有测试才用的** API（如 `restore_and_reroll()`），并让它在生产构建里不可达。

2. **`RunState: Clone + Serialize + Deserialize`**
   这是整个训练管线的基础设施：SL 重开、determinization 采样、回放对拍、并行 worker 都要它。一开始就做，别等需要了再补。

3. **`step` 是纯函数**
   `fn step(&mut self, action: Action) -> StepResult`，不依赖全局变量、不依赖墙钟时间、不读文件、不读环境变量。同一个 (state, action, rng) 必然得到同一个结果。

### SL 相关接口

```rust
fn snapshot(&self) -> Snapshot;                       // 含隐藏 RNG 状态
fn restore(&mut self, s: &Snapshot);                  // 原样写回，含隐藏 RNG
fn restore_and_reroll(&mut self, s: &Snapshot);       // ⚠️ 仅测试用，生产不可达
// 环境层（SL 语义）
fn begin_attempt(&mut self) -> AttemptId;             // 同一节点的新试次，隐藏状态不变
fn attempt_budget(&self) -> u32;                      // K，由环境强制
```

`attempt_budget` 必须是**环境强制的**，不能由策略自行决定（否则元策略会学会无限重开）。

## 2.3 内容数据驱动（这是"高抽象"的关键）

**不要给每张牌写一个类。** 卡牌/遗物/怪物/药水/事件全部是**数据表**：

```ron
// content/cards/ironclad.ron
Card(
    id: "bash",
    cost: 2,
    card_type: Attack,
    rarity: Basic,
    target: Enemy,
    effects: [ Damage(8), ApplyPower(Vulnerable, 2) ],
    upgrade: [ Damage(10), ApplyPower(Vulnerable, 3) ],
)
```

效果 DSL：

```rust
enum Effect {
    Damage(Expr),
    DamageAll(Expr),
    Block(Expr),
    ApplyPower { power: PowerId, amount: Expr, to: Target },
    Draw(u8), Discard { count: u8, choose: bool }, Exhaust { count: u8, choose: bool },
    GainEnergy(Expr), Heal(Expr), LoseHp(Expr),
    AddCard { card: CardId, to: Pile, count: u8 },
    Scry(u8), DoubleBlock, DoublePower(PowerId),
    Conditional { cond: Cond, then: Vec<Effect>, else_: Vec<Effect> },
    Custom(&'static str),   // 逃生舱：剩下 ~10% 的怪牌走 Rust 函数
}

enum Expr {
    Const(i32),
    PowerAmount { target: Target, power: PowerId },
    BlockOf(Target), HpOf(Target), HandSize, CardsPlayedThisTurn,
    EnergySpentThisTurn, X,
}
```

**规则：**

- DSL 只做"能覆盖 MVP 卡池的最小子集"。**不要试图设计一门通用脚本语言**——那是无底洞。
- 覆盖不了的走 `Custom("card_id")` + 一个 Rust 函数。允许脏，但要集中、要可 grep、要有测试。
- 好处：跟游戏版本对齐只改数据；数据表可 diff、可 lint、可当"卡牌知识"喂给模型（见 `docs/03` 的文本 embedding）。
- 写一个 **linter**：检查每个 effect 引用的 power/card/keyword 存在、数值在合理区间、没有循环引用。

## 2.4 RNG 纪律

StS1 的已知结构是**按用途分流的命名 RNG 流**（monsterRng / cardRng / shuffleRng / relicRng / potionRng …）。StS2 的具体命名与调用点**需从反编译源码确认**（`sts2.dll`，见 Alchyr 的 Decompiling wiki）。

```rust
struct RngSet {
    shuffle: Pcg64,      // 洗牌
    card: Pcg64,         // 卡牌奖励掉落
    monster: Pcg64,      // 遭遇选择
    monster_hp: Pcg64,   // 怪物血量浮动
    relic: Pcg64,        // 遗物掉落
    potion: Pcg64,       // 药水掉落
    event: Pcg64,        // 事件选择
    combat: Pcg64,       // 战斗内随机（随机目标、随机伤害）
    misc: Pcg64,
}
```

**规则：**

- 所有随机构造必须**显式传流**：`rng.shuffle.gen_range(0..n)`。禁止全局随机、禁止 `thread_rng()`。
- **分流结构必须与真机一致**。分流错误会导致分布漂移——比如真机"洗牌"和"掉落"用不同流，你合成一条，那么"抽到好牌"与"下一场遇到弱怪"就会产生真机不存在的相关性，模型会学到虚假规律。
- 每个 run 一个主种子派生所有子流（`stream = H(seed, purpose)`），保证可复现。
- 训练时每 episode 随机主种子，**种子绝不进入观测**。
- 提供 CLI：`--seed`、`replay(seed, actions) -> RunState`（回归测试的基础）。

## 2.5 数值正确性验证（可信度的唯一来源）

**没有对拍的模拟器不值得训练任何东西。**

| 层级 | 手段 | 覆盖 |
|---|---|---|
| **单卡** | 每张卡一个单元测试：打出后伤害/格挡/buff 层数/抽牌数断言 | 全部卡池 |
| **单怪** | 每个怪物一个测试：给定回合序列，断言伤害数值与意图序列 | 全部怪物 |
| **回放对拍** | 从真机取 `(种子, 动作序列, 逐步状态)`，在模拟器重放，逐帧比对 HP/格挡/能量/牌堆 | 端到端 |
| **不变量** | 随机自博弈 10⁶ 步，断言：HP ≤ maxHP、能量 ≥ 0、牌总数守恒（手牌+抽+弃+消耗+打出 = 常量）、回合数有上限、无死循环 | 全局 |
| **覆盖率** | 报告哪些卡/怪/交互尚未被任何测试触达 | 收尾 |

### 真机数据从哪来

- **STS2MCP**（`Gennadiyev/STS2MCP`）：暴露游戏状态给外部进程，是最直接的状态来源。
- **社区 run 数据**：spire-codex 收录了 run 记录，可用作补充（是否含逐步决策待核实）。
- **人工对局录制**：拿自己的几局，配合 mod 导出状态序列。少量（10–20 局）就足够抓出大部分机制错误。

对拍不合格的内容 → **直接从训练集里排除**，并在数据表里标 `verified: false`。宁可少 20 张牌，也不要让模型学错。

## 2.6 性能预算

| 指标 | 目标 | 说明 |
|---|---|---|
| 单核 | ≥ 5k 环境步/秒 | 纯规则、无特征化 |
| 单机（16 核） | ≥ 50k 环境步/秒 | 多进程 + rayon |
| 快照/恢复 | ≥ 100k 次/秒 | determinization 搜索的前提 |
| 特征化（GPU 侧批量） | 不成为瓶颈 | 逐样本 Python 特征化必然拖垮吞吐 |

**路线选择：**

- **原型阶段**：纯 Python，先求规则正确，不求快。这一步的价值是"想清楚机制"，不是性能。
- **训练阶段**：核心逻辑用 **Rust** 重写，通过 `PyO3 + maturin` 暴露 `sts2_core` 模块给 Python。Python 侧只做特征化调度与训练循环。
- 备选：先把整个 env 写成 batched tensor 运算（几千个实例并行）——适合喜欢纯 Python 的路线，但调试困难。

> **不要**在模拟器还只能跑 500 步/秒的时候就加大网络。先修环境吞吐。

## 2.8 环境接口（对齐 Gym 风格，但要说清楚差异）

```python
obs, info = env.reset(seed=...)          # seed 不进 obs！
obs, reward, terminated, truncated, info = env.step(action)

info["action_mask"]      # 合法动作掩码（必须提供，否则无效探索会毁掉训练）
info["is_action_valid"]  # 调试用
info["hidden_debug"]     # 仅测试构建可用；生产构建里不存在这个键
```

**动作空间的形态见 `docs/03` §3.5**——它是结构化的（`出牌/药水/结束回合 × 卡 × 目标`），不是扁平整数，环境与模型两侧要共用同一套定义（用 Rust 生成 Python 侧的枚举，避免两边漂移）。

**两个必须提供的调试能力：**

1. `env.render_text()`：把状态打印成人类可读的文本（"你的回合，能量 3，手牌：打击/打击/防御/痛击，敌人：颚虫 44/44 意图攻击 11"）。**这是排查机制错误和人工审查 agent 行为的唯一实用工具**，比任何可视化都重要。
2. `env.replay(seed, actions)`：复现任意一局。用于 bug 报告与对拍。
