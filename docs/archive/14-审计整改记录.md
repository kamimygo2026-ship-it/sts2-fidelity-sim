## 2. 逐条对照

### F01 · P0 · Run → 战斗丢失永久状态 —— ✅ 已修

**改之前**：`RunEnv._enter_node()` 只把 `card.cid` 传进 `start_combat()`，
于是升级状态、最大生命、进阶全部丢失。实测输出：

```text
Run 升级卡数 = 10       战斗升级卡数 = 0
Run 最大生命 = 120      战斗最大生命 = 80
战斗当前生命 = 105      → 出现"当前生命 > 最大生命"
Run 进阶 = 8            战斗进阶 = 0
```

**改法**：

* `core.combat_deck()` 把 Run 的永久牌组克隆成战斗副本，并写入
  `CardInstance.link_uid` —— 这是"永久卡牌关联"，让回写有**明确目标**而不是靠 `cid` 猜。
* `core.start_combat()` 新增 `player_max_hp` / `potions` / `max_energy` 参数；
  牌组参数接受完整实例（`str` 仍兼容，用于测试与旧调用点）。
* `CombatState.permanent_card_changes` 记录"战斗内发生的**永久**改牌"，
  `core.apply_permanent_changes()` 是唯一的回写函数。
* `RunEnv._sync_player_from_combat()` 是 Run←战斗的**唯一**回写入口：
  当前生命、最大生命、永久改牌、遗物持久计数、药水槽逐项显式列出。

**守住它的测试**：`tests/test_state_contract.py::TestRunCombatContract`（10 条，
含"未升级的牌不能被顺手升上去"与"战斗内生成的牌没有永久本体"两条反向验证）。

### F02 · P0 · 角色参数不决定初始状态 —— ✅ 已修

**改之前**：`RunEnv(character="silent")` 得到 HP 80 + 铁甲战士牌组 + 空遗物。

**改法**：

* `RunEnv.starting_state()` 从 `content.CHARACTERS` 取 HP / 金币 / 牌组 / 遗物 / 能量；
  内置占位内容没有角色表时退回占位常量，**只在 builtin 下发生**。
* 未知角色**直接 `KeyError`**，不静默退回默认角色。
* 顺带修掉一个隐藏缺陷：起始遗物只做了 `.lower()` 而不是 snake_case 归一化，
  `RingOfTheSnake` → `ringofthesnake` 与遗物表对不上，**初始遗物静默失效**。
* 新增 `content._character_gaps()` 收尾校验：角色定义的每一项都必须能对上加载后的内容表。

**守住它的测试**：`tests/test_state_contract.py::TestCharacterInit`（5 条）。

### F03 · P0 · 训练内容门禁没有落到采样器 —— ✅ 已修

**改之前**：`draft_pool()` 只筛"稀有度 + 有没有效果"，418 张里混进 223 张
`effects_incomplete`；`random_deck()` 跨角色混牌；`train_combat.py` 没有任何内容加载，
默认跑 12 张卡 / 3 只怪的内置占位内容而且没有提示。

**改法**：新增 `sts2_sim/eligibility.py`，把"哪些内容能进训练"变成唯一一处定义：

* 六个状态（已索引 → 已解析 → 可执行 → 闭包可执行 → 源码用例 → 参考验证），
  **只有前四层可自动判定**，后两层一律为未通过；
* 拒绝原因**可数、可排序、可归因**，不允许出现"其它"桶
  （`effects_incomplete` / `unimplemented_power` / `no_effects` / `closure_gap` /
  `triggers_incomplete` / `unsupported_op` …）；
* **依赖闭包**：卡可能生成、引用到的牌也必须合格，否则源卡也不算闭合；
* "诅咒/状态牌没效果"与"可打出的牌却什么都不做"**分开**判定 —— 前者是设计，后者是缺口；
* `assert_trainable()` 是训练启动门禁：内容未加载时**报错退出**，不自动退回 builtin
  （`allow_builtin=True` 只给单元测试与冒烟用，必须显式打开）。

`draft_pool()` / `encounter_pool()` / `random_deck()` 全部改为调用 `eligibility`，
`train_combat.py` 新增 `--content`，解析顺序是 `--content` > `STS2_CONTENT_DIR` >
本地默认目录 > 报错退出；启动时打印并保存内容/准入/词表三个指纹。

另外：遭遇表里成员数超过真机槽位上限（5）的记录在加载时被排除并计数
（`skipped_exceeds_slots`）—— 真机不可能同时站 6 只怪。

**守住它的测试**：`tests/test_state_contract.py::TestContentAdmission`（9 条）。

遗物与药水 token 是空占位；牌堆编码忽略升级标记。

### F05 · P0 · 怪物状态机条件输入不完整 —— ✅ 已修

**改之前**：`_choose_intent()` 构造 `MonsterContext` 时不传专属 flags/counters，
访问器把缺失值默认成 False/0，槽位被简化成 first/second。实测单独生成 Fabricator
初始意图是 `disintegrate` —— 而 `Fabricator.cs:51` 的 `CanFabricate`
（存活队友 < 4，**含自己**）为真，正确分支是随机召唤分支。

**改法**：

* `MonsterContext.flag()` / `counter()` 对**缺失值抛 `UnsupportedMechanic`**，
  不再默认 False / 0（`docs/13` §5）。调用方必须把真实运行状态算出来。
* `monster_ai.FLAG_RULES` 给每个已知标志标注来源与求值方式：
  `CanFabricate` / `CanLay` 是**从队友数量现算**，另外三个是**实例标志**；
  `COUNTER_SOURCES` 同理。`INSTANCE_FLAG_DEFAULTS` / `COUNTER_DEFAULTS` 在怪物入场时
  **显式初始化**（对应 C# 字段默认值），而不是"查不到就当假"。
* `EnemyState` 新增 `slot_name` / `ai_flags` / `ai_counters`；
  `core.init_enemy_ai()` 统一初始化并校验"条件里引用到的标志/计数器都已在登记表内"。
* 槽位名按真机序数（`first`…`fifth`，`Exoskeleton` 的条件就是 `SlotName == "third"`），
  召唤走 `core.next_open_slot()`（对应 `EncounterModel` 找第一个空闲槽位）。
  超出槽位表直接报错。

**守住它的测试**：`tests/test_monster_ai_runtime.py::TestRuntimeContextIsComplete`（8 条），
其中 Fabricator 两个方向（单只可造 / 满队不可造）都在。

### F06 · P0 · 伤害管线时序差异与出牌完成钩子 —— ✅ 已修

**改之前 1**：基础攻击 10 + 目标易伤 + 目标 3 层 Tainted，`compute_damage()` 返回 18；
源码是 `int((10+3)×1.5) = 19`。原因：`tainted_damage_bonus` 被放在乘法阶段之后，
而它是 `TaintedPower.ModifyDamageAdditive`，属于**加法阶段**。

**改之前 2**：卡牌效果遇到选择而挂起时，`step()` 仍立即调用 `on_card_played()` ——
`EnragePower` 这类"打出牌时触发"的能力会在效果还没结算完就先跑一轮。

**改法**：

* `compute_damage()` 把 tainted 挪回加法阶段，与力量同层。
* 新增 `core._fire_after_card_played()` 作为 `Hook.AfterCardPlayed` 的**唯一**触发入口，
  三个调用点：`step` 的 `play_card` 直通路径（仅在 `done` 时）、`_resolve_selection`
  续跑完成、`_autoplay_sly`。
  顺带补上一条旧实现**整个漏掉**的行为：自动打出的 Sly 牌也应当触发 `AfterCardPlayed`。

**守住它的测试**：`tests/test_damage_pipeline.py::TestAdditiveStageOrder`（5 条，
含反向验证）与 `tests/test_card_play_timing.py`（5 条）。

### 额外发现 · 端到端验证抓出的三个引擎缺陷 —— ✅ 已修

审计 F01–F12 都没列到这三条，它们全是在"真实内容 + SL 预算跑 1500 步"
和"整局 Run fuzz"里炸出来的 —— **单元测试一个都没覆盖到**。

**(1) 空候选选牌把环境卡死**（第 112 步）
效果链遇到"从弃牌堆选一张"时会挂起 `PendingSelection`，但候选本来就是空的时候
（弃牌堆为空），`legal_actions()` 返回**空列表** —— 环境既没有动作可发，也不会自己
往前走。实测触发点是**回合 1 的 `headbutt`**。改法：候选为空时当场跳过这次选择
（真机在没有合法候选时也不会向玩家提问）；候选**中途抽干**时按现有数量提前结束。

**(2) 抽牌不看手牌上限**（第 1000+ 步）
`ValueError: 手牌 数量 11 超过编码容量 10` —— 报错的是观测编码器，**根因在引擎**。
真机 `CardPileCmd.DrawInternal` 有三道闸门：`num = max(0, MaxCardsInHand - hand.Count)`、
循环里 `if (hand.Count >= MaxCardsInHand) break`（抽不下的牌**留堆**）、
以及 `CardPileCmd.Add` 往手牌加牌时若已满**改放弃牌堆**。
引擎一道都没有 → 手牌能到 11+，而那个状态在真机上不存在。
改法：抽牌与"入手牌"都走真机的闸门（新增 `core.add_to_hand`）。

**(3) 招式表闭包缺口**（整局 fuzz 的 seed=134）
`torch_head_amalgam` 的状态机首个状态是 `STRONG_TACKLE_MOVE`（伤害 26），
而社区库给的招式列表是 `tackle / tackle_2 / beam / tackle_3 / tackle_4` ——
**根本没有 26 点那一下**。运行到第 1 招就抛"状态机指向未知招式"，整局被打断。
改法分两层：

* `_load_monster_moves` 用**源码**（`move_values` 的意图与数值、
  `monster_moves.json` 的 `kills_self`）**补出**状态机需要而社区库没有的招式。
  意图类名只映射 `SingleAttackIntent` / `MultiAttackIntent`（都是"打伤害"，
  段数走 `times`）—— 其余**不猜**，因为意图是玩家据以决策的公开信息。
* 新增加载期**闭包闸门** `_enemy_move_gaps()`：任何怪物只要有状态机指向、
  招式表却没有的 move 状态，就把它所在的**遭遇**从遭遇表摘掉并计数
  （`docs/13` §7 的"闭包可执行"）。宁可少一组遭遇，也不要静默带洞跑 ——
  否则这个错误会等到那只怪真的出场才炸，可能是几十万步之后。
  `tools/healthcheck.py` 现在有一条独立检查盯这件事。

**守住它们的测试**：`tests/test_selection_index.py::TestEmptyCandidateSelection`（3 条）、
`tests/test_hand_limit.py`（8 条）、`tests/test_monster_move_closure.py`（9 条，
含"把补出来的招式拿掉，检测器必须重新报缺口"的反向验证）。

### F12 · P1 · checkpoint 与塑形 —— ✅ 部分修复

* `ppo.checkpoint_payload()` 保存权重 + 配置 + 优化器/调度器 + 内容指纹 + 词表指纹 +
  观察协议 + SL 协议 + 三个 RNG 状态；`verify_checkpoint()` 逐项比对并在不匹配时**报错**。
  触发条件很现实：内容变化后同名 embedding 下标会指向另一张牌，旧格式**无法察觉**。
* `ppo.shaped_reward()` 把势函数塑形收敛成一个函数，保证塑形项与 GAE 用**同一个 γ**
  （旧实现写死 γ=1，一旦改 gamma，"势函数不改变最优策略"的保证静默失效）。
* `PolicyValueNet` 的 embedding 尺寸改为**建网时现算**（原先 `N_CARDS = len(CARD_DB)`
  在 import 时求值，内容晚加载就会 `IndexError`），并在前向里校验词表版本一致。
* `evaluate()` / `evaluate_rulebot()` **把环境故障与策略输局分开计数**
  （`docs/13` §12.3）：故障局不进胜率分母，并留下复现用的种子与异常文本 ——
  否则一个环境 bug 会表现为"胜率下降"，没有任何信号。
* `RunBot` 的卡牌评分改为**按卡牌定义现算**：旧实现写死了一张内置占位卡 id 表，
  换真实内容后每张牌都拿默认分，规则 bot 退化成"永远选第一张"，
  而它是判断策略有没有进步的**那个基线**（`tests/test_runbot_baseline.py`）。

未做：GRU/序列记忆训练（`docs/13` §10.1 第 2、4 步）、按序列切分的 recurrent PPO。

### 5.3 药水抽取：一瓶被静默丢掉的药（收口）

事件侧留下一个 blocker：奖励药水 `foul_potion` 不在药水表里。根因是
`FoulPotion.TargetType`（`FoulPotion.cs:37-46`）是**按战斗状态分支的条件属性**，
而抽取器只认单个表达式 → 整瓶药被丢掉（65 个药水类只抽出 64 个）。

修法（`tools/extract_potions.py`）：条件声明不再导致整瓶丢弃，而是
**收集源码里出现的全部枚举值**、按"本引擎的使用语境是战斗内"选取，
并把"这是个条件声明"如实记进 `unsupported`（→ `effects_incomplete`，
所以它进不了训练集，但事件能引用到它）。

同时发现一个更危险的东西：`FoulPotion.OnUse` 有**三个分支**
（战斗内 / 商人 / 假商人事件），把整个方法体交给效果抽取器会把它们混在一起 ——
战斗内用这瓶药会**一边打伤害一边白拿 100 金币**。所以只抽战斗内那一段，
其余分支记为未建模。`tests/test_potion_extraction.py` 里有反向验证：
证明"整段抽"确实会混进 `gain_gold`。

⚠️ 过程中发现 `tools/extract_cards.py` 比生成已提交 `potions_source.json` 的那一版**更新**，
整体重跑会顺带改掉 6 个无关药水（例如 `gamblers_brew` 的 `discard` 变成
`select_card(purpose="choose")`）。这些改动需要逐个审查，所以本次**只并入**
`foul_potion` 一条，其余保持原样并在此记录 —— 一次只改一件事，否则出问题无法归因。

### 5.6 遗物钩子：本轮**没有**"补上"，而是先拆掉了三类假象

遗物是目标里点名的最后一块内容（109/299 有行为）。这一轮做的是**审计与门禁**，
结论是：**旧的"109 有行为 / 100 完全复刻"是虚高的**，真实数字是 **92 / 85**。
以下三条都会让模拟器**静默变强**，全部已修并加了护栏。

**(1) 把"记账"算成了"缺行为"（缺口虚高 55/280）**
``ArtOfWar.AfterCombatEnd`` 只写自己的私有字段（``AnyAttacksPlayedLastTurn = false``），
本身不改变任何游戏状态；``BrilliantScarf.AfterCombatEnd`` 只是 ``CardsPlayedThisTurn = 0``。
抽取器新增 ``classify_hook()``，把每个钩子分成
``commands``（体里有命令）/ ``query``（靠返回值改行为）/ ``bookkeeping``（只记账）。
实测 280 处缺口里 **55 处是记账**，不该算进"遗物缺行为"。

**(2) 选牌用途没过门禁（"完全复刻"是假的）**
``royal_stamp``（皇家印章）的 ``AfterObtained`` 是"从牌组里选一张**附魔**"，
而引擎没实现 ``enchant`` 用途 —— 运行期 ``runeffects`` 只打一行日志跳过。
旧实现把它算成"完全复刻"。现在 ``_relic_hook`` 会按时机校验选牌用途
（Run 层用 ``RUN_SELECTION_PURPOSES``、战斗内用 ``ENGINE_SELECTION_PURPOSES``），
用途不支持就判为缺口。实测拦下 **11 处**（``enchant`` / ``choose``）。

**(3) ⭐⭐ 源码里的条件被整批丢掉 → 钩子**无条件生效**（静默变强）**
这是本轮最重要的发现。抽取器只认"回合数守卫"和四个跨回合计数器，
于是下面这些条件**全部消失**，效果被当成"每张牌都触发 / 每回合都触发"：

| 遗物 | 源码条件 | 丢掉之后的错误行为 |
|---|---|---|
| ``happy_flower`` | ``(TurnsSeen + 1) % Turns == 0`` | 每 3 回合 +1 能量 → **每回合 +1** |
| ``kunai`` / ``shuriken`` / ``nunchaku`` | 仅攻击牌 且 ``AttacksPlayedThisTurn % N == 0`` | 每 3 张 +1 敏捷 → **每张都 +1** |
| ``ornamental_fan`` / ``iron_club`` / ``letter_opener`` | 同上（攻击/技能牌计数） | 同上 |
| ``war_paint`` / ``whetstone`` / ``fragrant_mushroom`` / ``sand_castle`` | ``Type == Skill/Attack`` + ``Take(N)`` + ``StableShuffle`` | 升级/转化**随机 N 张**、牌型不限 |
| ``parrying_shield`` / ``paels_tooth`` / ``distinguished_cape`` | ``Rng.CombatTargets.NextItem`` | 打指定目标 → 打**随机**目标 |

修法：``STATEFUL_CONDITIONS`` 增加五类模式（取模计数 / 牌型条件 / 集合取样 /
集合谓词 / 随机目标），命中就标 ``stateful`` → **拒绝采纳**（变成如实报出的缺口）。
实测判出 **42 个遗物** —— 它们此前都在模拟器里无条件生效。

⚠️ 唯一被显式排除的是 ``participants.Contains(base.Owner.Creature)``：
本模拟器是**单人**环境（``docs/13`` §5 第一交付范围），玩家永远是自己阵营的
participants 成员，该前缀**恒真**，丢掉它不改变任何数值。这条理由写在代码里，
并由测试盯住"它不该被任何模式误判"。

**顺带试过又撤回的一件事**：能力侧的 ``on_card_played`` / ``on_side_turn_end``
时机已经存在，给遗物补上同名的总线钩子看起来能一次解锁 18 个遗物 ——
**但正因为上面 (3) 还没修，那 18 个会全部无条件生效**。所以本批次把
``AfterCardPlayed`` / ``AfterSideTurnEnd`` 从 ``HOOK_TIMING`` 里**移出**，
并把启用前置条件写进代码注释（先让抽取器能建模这些条件，再打开这两个时机）。

**守住它的测试**：`tests/test_relic_hook_kinds.py`（17 条），
其中 ``test_no_adopted_hook_drops_a_condition`` 是**全量护栏** ——
它用**抽取器同一份**条件模式表扫一遍所有已采纳钩子的 C# 体，
任何一个带未建模条件就失败；外加"点名检查"与"门禁有牙齿"两条反向验证。

## 7. 第七批：地图与三幕流程（F08 的主体）

### 7.1 源码事实（先把它写清楚，再改代码）

真机一局走 **3 个幕索引**，但整个游戏有 **4 张幕地图**：

| 幕索引 | 地图 | `IsDefault` | 房间数 | 弱遭遇 | 营火配额 | 未知点偏移 |
|---|---|---|---|---|---|---|
| 0 | `Overgrowth`（密林） | true | 15 | 3 | `NextGaussianInt(7,1,6,7)` | 0 |
| 0 | `Underdocks`（暗港，需 `UnderdocksEpoch`） | false | 15 | 3 | `NextGaussianInt(7,1,6,7)` | 0 |
| 1 | `Hive`（蜂巢） | true | 14 | 2 | `NextGaussianInt(6,1,6,7)` | −1 |
| 2 | `Glory`（荣耀） | true | 13 | 2 | `NextInt(5,7)` | −1 |

依据：`ActModel.cs:261-279,528-596`、`ModelDb.cs:299-321`、四张 `Act.cs`、
`MapPointTypeCounts.cs:12-46`。地图几何：**7 列** × `GetNumberOfRooms(mp) + 1` 行，
远古点在 `(3, 0)`、Boss 在 `(3, GetRowCount())`（都在网格数组**之外**），
固定行是"最后一行营火 / `GetRowCount()-7` 宝箱 / 第 1 行怪"。
