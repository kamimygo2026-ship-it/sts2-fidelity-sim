## 1 · 敌人出招：已经能精确复刻

### ✅ L1-a 出招状态机：从 C# 提取完成

`tools/extract_monsters.py` → `data/content/repo/monster_ai.json`

```
扫描 121 个怪物类，提取出状态机 121 个
状态类型分布：{'move': 351, 'conditional': 17, 'random': 28}
```

**为什么必须从 C# 提取而不是用 codex JSON**：JSON 在这件事上**会丢控制流**。
`BowlbugRock` 的源码写的是链式赋值
`headbutt.FollowUpState = new ConditionalBranchState("POST_HEADBUTT")`，
JSON 却记成 `"next": null`——于是"Dizzy 之后回到 Headbutt"的转移整条消失。
`tests/test_monster_ai.py` 把这条差异固化成了断言。

提取器踩过的坑（都写进注释了）：
1. **构造函数参数取错括号**——state id 后面第一个 `(` 属于意图，不是构造函数；
   截错了会导致**所有** MoveState 的意图丢失（`_ctor_args`）
2. **带转型的声明** `MoveState x = (MoveState)(y.FollowUpState = new MoveState(...))`
   ——`=` 后面不是 `new`，变量名要与 `new` 分开匹配（漏了少 4 只怪）
3. **初始状态参数带转型** `new MonsterMoveStateMachine(list, (MoveState)x)`
   ——`([^)]+)` 会在转型的右括号处截断（漏了 19 只怪）
4. **条件初始状态** `MoveState initialState = (_flag ? a : b);`——需要别名递归解析
5. **`MaxInitialHp => MinInitialHp`**——常量引用，不能只认字面量
6. **`AddState` 被解析两遍**——条件分支重复记录

**已知残留**：4 个怪继承基类状态机（正确行为）；17 处意图参数未解析

### ✅ L1-b 状态机解释器：已接入引擎

`sts2_sim/monster_ai.py` —— `MonsterMoveStateMachine.cs` 的逐行翻译，**不是近似**。

实现并测试了的关键语义：

| 语义 | 源码依据 |
|---|---|
| 初始状态就是第一招 | `(!_performedFirstMove && IsMove) → return` |
| `next` 为空 → 回到初始状态 | `IsNullOrEmpty(next) ? _initialState : States[next]` |
| 非 move 状态一路走到 move 为止 | `do { … } while (!_currentState.IsMove)` |
| `MustPerformOnceBeforeTransitioning` 未满足不许转移 | `MoveState.CanTransitionAway` |
| `CannotRepeat` / `UseOnlyOnce` / `CanRepeatXTimes` / `cooldown` | `RandomBranchState.GetStateWeight` 逐行 |
| 条件分支按顺序取第一个成立 | `ConditionalBranchState.GetNextState` |
| 无匹配 / 无后继 → **抛异常**（不静默退化） | 源码同样抛 `InvalidOperationException` |

**RNG 分流也对齐了**：真机是 12 条命名流（`RunRngType`），出招走 `monster_ai`。
`RunRngSet.cs` 的注释还直接回答了 `docs/01` §1.8 的问题 3：
**遭遇/事件/遗物全在 `up_front` 里开局一次掷出**，而且**没有独立的卡牌奖励流**。

引擎集成验证（真实数据）：

```
Mawler  seed 7 : CLAW → RIP_AND_TEAR → CLAW → ROAR → RIP_AND_TEAR → CLAW → …
        seed 11: CLAW → ROAR → CLAW → RIP_AND_TEAR → CLAW → …
        ROAR 出现 1 次（UseOnlyOnce）| 无连续重复（CannotRepeat）| 初始招 CLAW
```

本轮又踩到 4 个坑（都写进注释）：

1. **`must_perform_once` 写在对象初始化器里**（`new MoveState(...) { MustPerformOnceBeforeTransitioning = true }`），
   没有变量前缀，靠 `x.MustPerform...` 正则找不到
2. **`follow_up=""` 与 `follow_up=None` 语义不同**：空 → 回初始状态；缺失 → 源码抛异常
3. **裸标识符当 flag 会掩盖拼写错误**：拼错的 flag 静默返回 False，出招悄悄走错分支。
   现在用白名单，未知标志直接抛 `UnknownCondition`
4. **类名驼峰 vs 数据 id 下划线**：`BowlbugRock` → `bowlbugrock` 对不上 `bowlbug_rock`，
   114 只怪只能匹配 30 只而且不报错
5. **加载顺序**：出招状态机必须在怪物表之后加载，否则一条都挂不上（`monster_ai: 0`，同样不报错）
6. **自环被去重吃掉**：单招怪写的是 `moveState.FollowUpState = moveState;`，
   我为了"避免冗余"加的 `!= target` 判断把自环也丢了，运行时变成"没有后继状态"直接抛异常

### ✅ L1-c 进阶数值：精确对齐

真机的进阶门槛（``AscensionLevel.cs``，**枚举序号就是进阶等级**）：

### ⭐ 抓到一个系统性偏差：逐次截断 vs 单次截断

真机管线（``Hook.ModifyDamageInternal`` + ``Creature.cs``）：

```
1. 加法    num += ModifyDamageAdditive(...)          （力量）
2. 乘法    num *= ModifyDamageMultiplicative(...)    （易伤/虚弱，**累乘**）
3. 钳制    num = min(num, ModifyDamageCap(...))
4. 落地    (int)Math.Clamp(amount, 0m, 999999999m)   （**只在最后截断一次**）
```

我们原来每步都 `int()` 截断一次：

```
base 7   虚弱+易伤   真机 7    旧实现 7    （碰巧一致）
base 9   虚弱+易伤   真机 10   旧实现 9    ← 差 1
base 13  虚弱+易伤   真机 14   旧实现 13   ← 差 1
```

只在特定数值组合下暴露的**系统性偏低**。现在用 `Decimal` 全程累乘、末尾单次截断。
`tests/test_damage_pipeline.py` 里有**反向验证**（证明逐次截断确实会算错），
否则这条测试没有鉴别力。

### ⭐ 第二个 bug：负值能力被静默删掉

`add_power` 原本把 `≤0` 的能力一律 `pop`，但真机的**力量可以为负**
（``powers.json`` 有 ``allow_negative`` 字段，卡牌里也有"失去 2 点力量"）。
结果是"力量被削成负数"悄悄变成"力量为 0"。现在 `strength` / `dexterity` 允许负值。

## 5 · 数据卫生：一次"删掉重复导入"引出的连锁问题

用户的要求是"先筛选一下导入的数据，把重复导入的删掉"。审计结果：**归一化后的表里
一条重复都没有** —— 但审计过程本身把之前几轮"修重复"时引入的 bug 全抖了出来。
教训一致：**每一次"修去重"都在另一个方向制造静默丢失**，必须两边同时钉住。

### 审计方法与工具

`tools/audit_data.py`（新增）做三件事，每件都可复现：

1. **按主键查重、按名字查重**；
2. 把 raw 与归一化结果的条数**逐数据集对账**（一个都不许少）；
3. 按磁盘实况**重建 manifest**。

⚠️ 查重的第一个坑：**主键字段名不统一** —— `cards` 用 `cid`、`monsters`/`encounters`
用 `eid`、其余才叫 `id`。一律用 `record["id"]` 会得到 `id唯一=1`（全是 `None`）这种
"零重复"的假象。第一次查重就是这么被骗过去的。

重名审计也必须是**规则化**的，不能手工列白名单：`FAKE_*` 遗物（`Anchor` vs
`Anchor???`）、5 个角色各自的基础牌（`strike_ironclad`…）都是合法的。见
`tests/test_data_integrity.py::_explain_collision`。

## 6 · L3 卡牌效果：从**描述文本**改为**反编译源码**

用户的要求是"修正卡牌效果解析（577 张全量）"。结论：**解析描述文本这条路本身
就是错的方向**，改为从 C# 抽效果。

### 为什么必须换方向

英文描述是给人读的。`"Deal 8 damage. Apply 2 Vulnerable."` 这类句式能覆盖一半，
但 `"At the start of your turn…"`（40 处）、`"At the end of your turn…"`（22 处）、
`"Whenever you play a card…"` 这些**永远解不准**。而 C# 里写的是**可执行代码**：

```csharp
// Bash.cs —— 效果、数值、目标全在这里
protected override IEnumerable<DynamicVar> CanonicalVars => ...(new DynamicVar[2] {
    new DamageVar(8m, ValueProp.Move), new PowerVar<VulnerablePower>(2m) });
: base(2, CardType.Attack, CardRarity.Basic, TargetType.AnyEnemy)
await DamageCmd.Attack(base.DynamicVars.Damage.BaseValue).FromCard(this, cardPlay)
    .Targeting(cardPlay.Target).Execute(choiceContext);
await PowerCmd.Apply<VulnerablePower>(choiceContext, cardPlay.Target,
    base.DynamicVars.Vulnerable.BaseValue, base.Owner.Creature, this);
protected override void OnUpgrade() {
    base.DynamicVars.Damage.UpgradeValueBy(2m);
    base.DynamicVars.Vulnerable.UpgradeValueBy(1m); }
```

### 关键设计：量存**变量引用**，不存死数字

源码的升级改的是**基础值**（`UpgradeValueBy`），不是"升级后再加一段效果"。
所以效果里存 `amount_var="Damage"`，升级版由 `基础值 + 升级增量` **算出来**。
这样升级前后**不可能对不上** —— 而抄两份数字一定会对不上。

## 8 · L3 续：把"选一张牌"做成一等动作

上一节留下的最大单块缺口是**玩家选牌**。追下去发现它不止影响那 13 张直接调用
``CardSelectCmd`` 的卡 —— ``CardPileCmd.Add`` 与 ``add_card`` 的失败案例**同样
源于选牌**（``cardModel`` 来自选择），``exhaust`` / ``discard`` 亦然。
所以这是**一个根因、四个症状**。

### 设计：挂起 + 续跑，而不是"跑完再补一刀"

真机的效果序列是 `抽牌 → 选牌 → 弃牌`。若把选牌拆成"先跑完全部效果、
再单独问一次"，顺序就会错 —— ``acrobatics`` 是"抽 3 再弃 1"，
反了会变成"弃 1 再抽 3"，**候选池少 3 张**，玩家能做的选择完全不同。

所以 ``select_card`` 是效果序列里的一个**算子**：执行到它就挂起，
把剩余效果存进 ``PendingSelection.rest``，选完再续跑。

| 概念 | 落地 |
|---|---|
| 挂起点 | ``CombatState.pending``（非空 = 正在选牌） |
| 候选牌 | **每次从牌堆现算**，不存下标快照（选一张后下标会移位） |
| 动作 | ``Action("select_card", hand_index=i)``；挂起期间**只有**它合法 |
| 打出的牌 | 挂起时留在 ``play_area``，续跑完成后才落进弃牌堆 / 消耗堆 |
| 观测 | ``selecting_purpose`` / ``selecting_remaining`` + 3 列全局特征 |

### 抽取层的两个坑（都属于"看起来对、其实反了"）

**1. 嵌套调用会把顺序颠倒。** 两种写法：

```csharp
// Acrobatics：分句写 —— 位置顺序就是正确顺序
await CardPileCmd.Draw(choiceContext, base.DynamicVars.Cards.BaseValue, base.Owner);
CardModel cardModel = (await CardSelectCmd.FromHandForDiscard(…)).FirstOrDefault();
await CardCmd.Discard(choiceContext, cardModel);

// Prepared：嵌套写 —— CardCmd.Discard 在文本里**更靠前**
await CardCmd.Discard(choiceContext, await CardSelectCmd.FromHandForDiscard(…));
```

按出现位置排序会把 `Prepared` 排成"先弃后选"。正确做法是看**括号包含关系**：
若某条 `Discard`/`Exhaust` 的参数括号里含一次选牌，它只是外层包装。

**2. 包装层的 Discard/Exhaust 要丢掉**，否则引擎会弃两次（或报"未知算子"）。

### 顺带修掉的三个静默 bug

| 症状 | 根因 |
|---|---|
| 选牌时规则 bot 返回 `end_turn`（**非法动作**） | `RuleBot.act` 只找 `play_card`，没找 `select_card`。`survivor`（格挡+弃牌）被打出后下一次调用就会炸 |
| 加三列特征后**整个模块 import 失败** | `NUM_FEATURES = 20` 是手写魔数，与 `FEATURE_LAYOUT` 重复维护。改为 `len(FEATURE_LAYOUT)` 推导 |
| lint 把 `select_card` 报成"未知算子" | `lint()` 里另抄了一份算子表。改为共用 `ENGINE_OPS` |
| 生成的卡身份不可靠 | `CardInstance.uid` 默认 0，而 `uid` 参与相等性、牌堆用 `list.remove(card)`（按 `==` 找第一个）—— "选中的那张"与"被移除的那张"可能不是同一张。改为自动分配唯一 uid |

## 9 · L3 续：手牌触发器与 duration 时机

这一轮从"选牌之后去哪"（`CardPileCmd.Add`）查起，最后挖出**两个让模拟器
比真机简单**的机制缺失。

### ⭐ 手牌触发器被整块丢弃（12 张卡）

`cards_source.json` 一直抽出了 `triggers`，但 **`CardDef` 根本没有这个字段** ——
12 张卡的触发器被静默丢弃。而这 10 张 `on_turn_end_in_hand` 正是
**敌人塞给你的状态/诅咒牌**：

| 卡 | 触发器 |
|---|---|
| `burn` / `decay` | 回合结束时若在手里，受到 2 点伤害 |
| `infection` / `wither` | 3 点 |
| `toxic` | 5 点 |
| `doubt` | 获得 1 层虚弱 |
| `bad_luck` / `beckon` | 掉 13 / 6 点血 |

不接它们，模型会学到"手里囤燃烧牌没代价"，而真机里是要掉血的。
**这是"模拟器比真机简单"这一类最危险的缺口：模型会主动利用它。**

顺带发现采用条件写错：`if not base and not upgraded: skip` —— 把"只带触发器、
没有 OnPlay 效果"的卡**整条跳过**。`burn` / `decay` / `infection` 全是这样。

### ⭐ duration 递减时机：条件是 `side == Enemy`，不是"拥有者阵营"

三个 duration 能力的源码**完全一致**：

```csharp
// VulnerablePower / WeakPower / FrailPower
public override async Task AfterSideTurnEnd(… CombatSide side …) {
    if (side == CombatSide.Enemy) await PowerCmd.TickDownDuration(this);
}
```

我原来在"拥有者阵营回合结束"递减，于是**玩家身上的易伤在玩家回合结束就掉了一层** ——
"敌人先给你上易伤、再打你"这类联动会少算一整个回合的量。正确时机是
**敌方阵营回合结束时，对场上所有持有者一起递减**。

### ⭐ 弃手牌时 Ethereal 是"消耗"而不是"弃掉"

`CombatManager.ResolveTurnEndCardEffects`：带 `Ethereal` 关键字时走
`CardCmd.Exhaust`，否则才 `CardPileCmd.Add(…, PileType.Discard)`。
一律弃掉会让这 18 张牌一直在牌库循环 —— **变相加强**。

### 牌堆移动（`CardPileCmd.Add`）

| 形态 | 处理 |
|---|---|
| `Add(this, PileType.Y)` | 新算子 `move_self_to_pile` |
| `Add(<选牌>, PileType.Y, [Pos])` | 选牌的用途由**外层**决定：`to_hand` / `to_draw` |
| `Add(item/cards/array, …)` | 局部集合（"所有 0 费牌"）→ 需谓词支持，**暂不支持** |

抽取层踩了三个坑：

1. **用途可能后置**（分句写法：先选牌赋给局部变量，后面 `Add` 才说明去哪）→
   必须先占位、等外层来补。
2. **占位时不能把 `from`/`count` 一起丢掉** —— 硬编码成 hand/1 会让
   "从弃牌堆选"变成"从手牌选"（实测 `hologram` 的候选数变成 0）。
3. **`resolve_pile` 只能看顶层参数**：`Add(await FromCombatPile(ctx,
   PileType.Discard…), PileType.Hand)` 里有**两个** `PileType`，整串正则搜到的是
   嵌套选牌的**来源**牌堆，于是 `Dredge` 被判成"选完放进弃牌堆"，正好相反。

### 又一个"伤害打到谁"的静默错误

`_apply_one` 的 `damage` 分支**忽略 `eff.target`**，一律走 `_primary_target`。
卡牌伤害通常打敌人所以一直没暴露，但触发器的 `target` 是 `self` ——
于是"在手里烧你"变成了"**在手里烧敌人**"，状态牌的代价直接反号。
（同一类错误第二次：第一次是怪物攻击目标永远取"敌人列表"，见 §1。）

## 10 · L4 充能球（Defect 的核心机制）

这是剩余最大的一块算子缺口（`channel` 21 张）。数值与时机全部抄自
``MegaCrit.Sts2.Core.Models.Orbs.*``：

| 球 | Passive | Evoke | 触发时机 | 目标 |
|---|---|---|---|---|
| Lightning | `ModifyOrbValue(3)` | `ModifyOrbValue(8)` | 回合结束 | 随机敌人 |
| Frost | `ModifyOrbValue(2)` | `ModifyOrbValue(5)` | 回合结束 | 自己（格挡） |
| Dark | `ModifyOrbValue(6)` | 累计值（初值 6） | 回合结束 | 最低血敌人 |
| Glass | `ModifyOrbValue(当前值)`（初值 4） | `PassiveVal * 2` | 回合结束 | 全体敌人 |
| Plasma | `1`（**不吃 Focus**） | `2` | **回合开始** | 自己（能量） |

### 三条容易搞错、错了就静默偏掉的语义

**1. 球的伤害/格挡带 ``ValueProp.Unpowered``** —— 不受力量 / 虚弱 / **易伤**影响，
但**可以被格挡**。所以它既不能走 `deal_damage`（会乘上力量与易伤），
也不能走 `deal_raw_damage`（那是"不可格挡"的中毒/荆棘通道）。
Defect 的伤害大半来自球，误差会直接反映成胜率差 ——
为此新增了 `_orb_raw_damage` / `_orb_gain_block` 两个专用通道。

**2. ``ModifyOrbValue`` 才是 Focus 的作用点**，而 `PlasmaOrb` 用的是裸
``1m``/``2m`` —— 所以"Plasma 不受 Focus 影响"是**源码层面的事实**，
不是平衡说明。给它加上 Focus 会让每回合凭空多出能量。

**3. Dark 与 Glass 有跨回合状态**：
`DarkOrb._evokeVal` 初值 6、每次回合结束 `+= PassiveVal`（吃 Focus）；
`GlassOrb._passiveVal` 每次触发先 `max(0, value - 1)` 再造成伤害。
当成无状态会让 Dark 永远只能 evoke 6、Glass 永远不减。

### 槽位溢出：激发**最左边**那个，不是丢弃新球

`orbs.channel` 在槽满时先 `evoke(0)` 再追加。搞反的话球的节奏完全变样 ——
激发会打伤害，丢弃不会。

### 又一个"静默变成空卡"的漏洞

采用逻辑里原本写着
``if existing is not None and existing.effects: 标记残缺``。
那个 ``and existing.effects`` 让"源码版被拒 + 文本版也没效果"的卡
（典型是 `chaos` 引导**随机**球）既没有效果、也**没被标记** ——
静默变成一张打出去什么都不发生的空卡。

去掉条件后，标记数从 210 → **272**，可用卡从 379 → **317**。

⚠️ 中途我报过 379（64.3%），那是被 62 张"没有效果"的卡**虚高**的。
**317（53.8%）才是诚实的数字** —— 其中 269 张是"可打出但打出去什么都不发生"，
正是最该排除出训练集的一类。

## 11 · ⭐ 怪物固有属性：40% 的怪开局是"换了一只怪"

做集合过滤时 ROI 太低，于是回头**量了一遍全局缺口**，结果发现这一块：

|---|---|
| 带固有属性的怪 | **46 / 115（40%）** |

两个独立的问题叠在一起：

1. **导入器把数值丢了**。原始数据里写着
   `aeonglass: [{"power_id": "ARTIFACT", "amount": 3}]`，
   而归一化后只剩 `unmodeled_innate_powers: ["artifact"]` ——
   `artifact 3` 与 `artifact 1` 是完全不同的战斗。
2. **引擎从不在开战时施加**。`start_combat` 里根本没有这一步，
   于是 `aeonglass`（一只 Boss）的核心机制直接不存在。

这属于最难发现的一类：**没有报错、没有警告，只是这只怪变弱了**。

### 修复

* 导入器：固有属性**连数值一起**保留（`power` / `amount` / `amount_ascension`）。
* `EnemyDef.innate_powers` + `start_combat` 在入境时施加
  （对应真机的 `AfterAddedToRoom`）。
* `engine_coverage()` 增加"仍有未实现固有属性的怪物数"与按频次排序的清单 ——
  缺 3 只怪的属性和缺 37 只怪是两件事，必须能看出来。

### 顺带实现 `ArtifactPower`（8 只怪，最高频）

```csharp
public override bool TryModifyPowerAmountReceived(… ) {
    if (target != base.Owner) return false;
    if (canonicalPower.GetTypeForAmount(amount) != PowerType.Debuff) return false;
    if (!canonicalPower.IsVisible) return false;
    modifiedAmount = 0m;  return true;      // 完全抵消
}
// 然后 AfterModifyingPowerAmountReceived → PowerCmd.Decrement(this)
```

**`GetTypeForAmount` 会让带负值的类型翻转**（照抄，别简化）：
`Counter` + `AllowNegative` + 负数 → 算 Debuff；不允许负值的 Debuff + 负数 → 算 Buff。
这决定了"给带神器的怪上负力量"该不该被抵消 ——
弄错会让该挡的没挡、不该挡的挡了。

⚠️ 已知近似：引擎没有"隐藏能力"（`IsVisible`）的概念，一律当可见。
写在这里而不是藏着。

## 12 · L5 起步：药水（64 个）+ ⭐ `ValueProp` 这条被忽略的管线

### 药水与卡牌同构，机械全部复用

| 卡牌 | 药水 | 说明 |
|---|---|---|
| `OnPlay(ctx, play)` | `OnUse(ctx, target)` | 效果方法 |
| `CanonicalVars` | `CanonicalVars` | 同一套 `DynamicVar` / `PowerVar<T>` |
| `CardType` | `PotionUsage` | 何时可用 |
| `TargetType` | `TargetType` | 目标 |

所以 `tools/extract_potions.py` 直接复用卡牌抽取器的 `parse_vars` /
`extract_effects` / `resolve_amount`。**目标由声明的 `TargetType` 决定**，
不去猜 `target` 形参指谁（单人游戏里 `AnyPlayer` 就是自己）。

成果：64 个药水，50 个有可执行效果，**41 个可直接使用**；与社区库对账
**62/63 吻合**（只有 `ambergris` / `deprecated_potion` 是源码独有）。

### ⭐ 抓到一个系统性缺陷：`ValueProp` 被完全忽略

真机把"这个量走不走修正管线"声明在变量上：

```csharp
new DamageVar(20m, ValueProp.Unpowered)   // 火焰药水
new BlockVar(12m, ValueProp.Unpowered)    // 格挡药水
new DamageVar(6m,  ValueProp.Move)        // 打击（普通攻击）
```

`Unpowered` = **不经过力量/虚弱/易伤（伤害）或敏捷/脆弱（格挡）的修正，
但仍然可以被格挡**。而我此前对 `ValueProp` 一无所知，于是：

**实测火焰药水打出 25 而不是 20** —— 玩家身上的 5 点力量被算了进去。

这不是药水独有的问题：**充能球也是 `Unpowered`**（我上一轮是靠硬编码
`_orb_raw_damage` 绕过的，属于碰巧对上）。现在改成**从源码抽 `ValueProp`
并传染给引用它的效果**，`deal_damage(..., unpowered=...)` 统一处理。

⚠️ 与 `Unblockable` 的区分必须写对：`Unpowered` **不等于**不可格挡。
弄混会让药水伤害穿透格挡 —— 又一个"看起来正常但一定算错"。

### 残缺的药水**拒绝使用**

`PotionDef.effects_incomplete` 的药水直接抛异常。用一瓶"少了一半效果"的药水
等于给模型一个错误的强度，比不让用危险得多。当前 23 个残缺，
聚类与卡牌完全一致（随机牌池 5、选牌 4、召唤/铸造/自动打出各 1）。

**局部变量的成员访问**：真机常写
``var damage = base.DynamicVars.Damage;`` 之后用 ``damage.BaseValue``。
只支持"整串是变量名"会漏掉这一大类写法 —— 实测 `fire_potion` /
`explosive_ampoule` 的伤害量因此解析不出、整瓶药被标残缺。

## 14 · 商店：结构、价格、RNG 流全都对不上

### 1. 商店在抽铁甲战士的牌

### 2. 价格是凭空编的

### 3. ⭐ 结构也不对：商店是「**每种类型各一格**」

```csharp
private static readonly CardType[] _coloredCardTypes =
    { CardType.Attack, CardType.Attack, CardType.Skill, CardType.Skill, CardType.Power };
int num = Player.PlayerRng.Shops.NextInt(_coloredCardTypes.Length);   // 只是轮转顺序
```

**5 个格子，类型固定为攻击/攻击/技能/技能/能力**。每格先用商店概率摇稀有度，
再在「该稀有度 + 该类型」的池里选一张；该组合空了就退到下一个允许的稀有度
（``GetNextAllowedRarity``）。

旧实现"按稀有度随机抽 3 张"连**格子数和类型结构**都不对 ——
真机永远不会出现"五个格子全是能力牌"。

### 4. ⭐ 更正一处我自己的错误结论：RNG 流是**两层**

本文件与 ``rng.py`` 早先都写着"真机**没有独立的卡牌奖励流**，奖励也来自
``up_front``"。**那是查漏了。** 真机有两层：

| 层 | 枚举 | 内容 |
|---|---|---|
| run 级 | ``RunRngType``（12 条） | 预掷 / 洗牌 / 怪物 AI / 战斗内各类随机 |
| **玩家级** | ``PlayerRngType``（3 条） | **``Rewards`` / ``Shops`` / ``Transformations``** |

所以卡牌奖励走 ``rewards``、商店走 ``shops``、变形走 ``transformations``。
借错流会让"抽到好牌"与"下场遇弱怪"产生真机不存在的相关性 ——
而模型会认真学到那个虚假规律。

已在 ``rng.STREAMS`` 里补上这三条，并把两处错误注释改正。

### ⭐ 时机必须照抄 `CombatManager`，不能凭感觉

真机的玩家回合开始顺序（`CombatManager.cs:688-927`，逐行核对过）：

| 顺序 | 真机钩子 | 对应遗物 |
|---|---|---|
| 1 | `Creature.BeforeTurnStart` | 能力快照 `AmountOnTurnStart` |
| 2 | **`Hook.BeforeSideTurnStart`** | 弹珠袋、破碎核心、力量电池、红面具 |
| 3 | `Creature.AfterTurnStart` → **`ClearBlock`** | ⚠️ **玩家第 1 回合豁免**（`Creature.cs:686-697`） |
| 4 | `ResetEnergy` | 能量重置 |
| 5 | **`Hook.AfterEnergyReset`** | 战争艺术、古茶具 |
| 6 | **`Hook.BeforeHandDraw`** + `ModifyHandDraw(…, 5m)` | 准备背包（+2）、大蘑菇（−2） |
| 7 | `CardPileCmd.Draw` | 基础抽 **5** 张 |
| 8 | **`Hook.AfterPlayerTurnStart`** | 皇家毒药、赌徒筹码 |
| 9 | **`Hook.AfterSideTurnStart`** | 提灯、赤備、铜鳞 |
| 10 | `OrbQueue.AfterTurnStart` | 充能球的回合开始 |

顺手修掉两个**已经存在**的时序错误：

* 旧引擎在回合开始**无条件**清格挡 → 锚的 10 点开局格挡会被立刻清掉。
  真机对**玩家第 1 回合**豁免清格挡，这正是开局格挡遗物能生效的原因。
* 旧引擎把 `AfterSideTurnStart`（能力规则的 `on_turn_start`）跑在**抽牌之前**，
  真机是**之后**（中毒掉血、下回合格挡都在手牌到手之后结算）。

### ⭐⭐ 最危险的一处：条件极性

真机里同一个 `if`，在两类钩子里含义**正好相反**：

```csharp
// 数值钩子：排除式 —— 条件成立就 return，"满足则不生效"
public override decimal ModifyHandDraw(Player player, decimal cardsToDraw)
{
    if (base.Owner.PlayerCombatState.TurnNumber > 1) return cardsToDraw;
    return cardsToDraw + base.DynamicVars.Cards.IntValue;      // 只在第 1 回合多抽 2 张
}

// 效果钩子：包含式 —— 条件成立才执行效果
public override async Task AfterSideTurnStart(...)
{
    if (participants.Contains(base.Owner.Creature) && ...TurnNumber <= 1)
    {
        await PlayerCmd.GainEnergy(base.DynamicVars.Energy.BaseValue, ...);  // 只在第 1 回合给能量
    }
}
```

第一版把两者**都**当成"命中则不生效"，于是：

| 遗物 | 错误结果 | 正确结果 |
|---|---|---|
| 提灯 | 第 **2** 回合起每回合 +1 能量 | 只在第 **1** 回合 +1 能量 |
| 弹珠袋 | **永远**不上易伤 | 第 1 回合给全体敌人上 1 层易伤 |
| 扭转漏斗 | 第 2 回合起每回合给全体上 4 毒 | 只在第 1 回合 |
| 风箱 | 第 2 回合起升级手牌 | 只在第 1 回合 |

四种都是"数值全错、日志完全正常"。修法：按条件后面跟的是 `return` 还是效果体
判定极性（`conditional_blocks`），极性一路带进 `relics._applies`。

⚠️ 判定函数本身还踩过一次 `balanced()` 的返回值坑：它返回的是**右括号的下标**，
从那里开始切片会切到 `)` 自己，于是**永远**判不出 `return`，全部条件都被当成
包含式。症状是 `TwistedFunnel` 的"跳过"被判成"生效"。

### ⭐ `all_enemies` 被静默塌缩成单体目标

`content._resolve_effects` 里有一行 ``if target == "all_enemies": target = "enemy"``。
对**伤害**来说这没问题（有 `damage_all` 算子），但对 `apply_power` 是致命的：
`philosophers_stone`（给**所有**敌人 +1 力量）与弹珠袋（给**所有**敌人上易伤）
都只会命中第一个目标，而日志照常打印"获得 1 点力量"。

同一个根因还在抽取器里：`HittableEnemies`（**复数集合**）和 `cardPlay.Target`
（单体）被归进了同一个桶。两处一起修，并加了"从集合里取单个"的排除规则
（`.First()` / `.Take()` / `.GetRandom()` 不算全体）。

### ⭐ 具名变量：77 处变量值被静默丢弃

真机的变量有两种写法：


### 数值层：算不出的**一律不采纳**，并且必须可见

遗物的每回合能量/抽牌是最有训练价值的一层（12 个加能量、11 个改抽牌）。
采纳规则是"宁可少一个，也不能让遗物比真机更强或更弱"：

* **条件算不出就不采纳**：`TurnsSeen`（每 3 回合多抽 1 张）、`KindleCount`、
  未识别的守卫 —— 共 11 条进了 `relics_unresolved_numeric`。
* **有战斗阶段缺口就不采纳数值半边**：`bread`（面包）的 `ModifyMaxEnergy` 抽得出
  "+1 能量（第 2 回合起）"，但它的另一半在第 1 回合 `PlayerCmd.LoseEnergy(2)` 没实现 ——
  只采纳前一半等于把一个负面遗物变成纯收益。天鹅绒项圈同理（+1 能量但少了
  "每回合最多 6 张牌"的限制）。

配套测试 `test_no_relic_silently_loses_its_numeric_effect` 断言这条不变量：
**带数值钩子的遗物，要么被采纳，要么出现在未采纳清单里，中间不许有静默的洞。**

健康检查此前一直在内置模式下静默少跑一整段。修好后内置与真实内容**两种模式都 31/31**。

## 16 · ⭐ 敌人 buff：一次把 31 个能力落地（27 → 58）

`tools/power_worklist.py` 扫所有怪物类里的 ``PowerCmd.Apply<T>``，

## 17 · 招式落实：敌人终于会"做它该做的事"了

§16 把 31 个敌方能力实现了，但它们**还打不到** —— 因为招式效果仍来自社区库，
而社区库把这类效果整段漏掉了。这一节把最后一块拼上。

### 问题有多大

| 事实 | 数值 |
|---|---|
| 源码里有怪用招式上 `frail` | **14 处** |
| 社区库记录的这些效果 | **0 处** |
| 有 buff/debuff 意图、效果却是空的招式 | **39 条**（涉及 35 只怪） |

所以 `frail` 这个基础 debuff 在模拟器里**一次都不会触发** —— 不是能力没实现，
是没有任何招式施加它。

### 做法：复用卡牌的效果抽取器

怪物招式处理函数体用的是**和卡牌同一套命令**（`PowerCmd.Apply` /
`CreatureCmd.GainBlock` / `CardPileCmd.AddToCombatAndPreview`…），
所以直接复用 `extract_cards.extract_effects`，只做两处适配：

1. **常量内联**。卡牌写 `base.DynamicVars.Damage`，怪物写裸标识符
   （`IncantationAmount` / `BiteDamage`）。先把函数体里的常量名换成字面量再抽。
   ⚠️ 替换必须**跳过字符串字面量**：`TalkCmd.Play("DevourStartTrigger", …)`
   这类文本里的词一旦被替换，抽出来的就是垃圾效果，而且不报错。
2. **进阶值单列**。真机写 `GetValueIfAscension(DeadlyEnemies, 32, 26)` ——
   A9 起数值不同。内联普通值，进阶值另存一份，由引擎按当前进阶选择。

顺带把三类命令从"未支持"里摘出来（它们一个数值都不影响，却让整批招式被判残缺）：

* **装饰/纯表现**：`TalkCmd.Play` / `SfxCmd.*` / `VfxCmd.*` / `ThinkCmd.Play`
* **`DamageCmd.Attack` 的链式配置**：伤害数值由**意图**给出，这些只是修饰符
* **目标写法 `base.Creature`**：怪物的所有招式都用它指自己（卡牌写
  `base.Owner.Creature`）。不认它，"这只怪给自己上 buff"会全部落成
  `target: unknown` —— 实测 60+ 处

另外新增了一条真实效果算子的支持：`CardPileCmd.AddToCombatAndPreview<T>`
（往玩家牌堆塞 N 张状态牌），不认它 `Chomper.ScreechMove`（尖啸塞 3 张眩晕）整条丢失。

### ⭐ 差点造成灾难性回归：攻击招式的伤害

真机的怪物伤害来自**意图**（`SingleAttackIntent(Damage)` →
`DamageCmd.Attack(Damage).FromMonster(this)`），招式函数体里**没有**独立的伤害命令。
把 `DamageCmd.Attack` 归入"装饰"之后，攻击招式的效果列表变成空的 ——
而 `core._effective_effects` **只在已有 `damage` 效果时**才用意图数值覆盖，
于是敌人**永远打不出伤害**。

实测：**221 个攻击招式里 197 个丢了伤害**，表现是"玩家打完一整场没掉血"。

抓到它的是 `test_vulnerable_is_active_during_the_enemy_turn`
（断言"易伤在敌方回合仍然生效"，结果玩家掉血 0）。这条测试当初是为**递减时机**
写的，却意外拦住了一次完全不相干的回归 —— 这就是"测试要能分辨好坏"的价值。

修法：`_with_intent_damage()` —— 招式有数值却没有 `damage` 效果时，
按意图补上 `damage × times`。**数值仍来自源码**（`move_values` 的进阶/普通两档），
这一步只负责把"这一招是攻击"表达成效果。
修完 224/226 有伤害；剩下 2 条是**运行期决定伤害**的招式（`the_forgotten.dread`、
`waterfall_giant.pressure_gun`），已进台账。

### ⭐ 一个统计口径的坑：计数不能只看"值变了"

第一版把 `adopted` 只在"新效果 ≠ 旧效果"时累加。后果是**同一份内容加载两次得到
两个不同的数字**（第一次 239、第二次 75）—— 统计就没法当台账用了，
而且这种偏差只在"内容已经加载过"的路径上出现（测试里就是）。

判据改成"这条招式**采纳了源码**"，与当前值是否相同无关。现在两次加载都是 284/36。

### ⭐ 最大生命的两个方向（被用户纠正的一处）

我一开始把 `gain_max_hp` 实现成"只加上限、不回血"，因为读源码时
**只看了方法的前十行**。用户指出后重读，`Heal` 在**方法最后一行**：

```csharp
// CreatureCmd.cs:841-854
decimal num = await SetMaxHp(creature, (decimal)creature.MaxHp + amount);
...
await Heal(creature, num);          // ← 加多少上限就回多少血
```

`LoseMaxHp`（同文件 866-882）则是：

```csharp
decimal newMaxHp = (decimal)creature.MaxHp - amount;
if (newMaxHp < (decimal)creature.CurrentHp)
    await Damage(context, creature, CurrentHp - newMaxHp, Unblockable|Unpowered, …);
await SetMaxHp(creature, Math.Max(1.0m, newMaxHp));
```

只砍血槽、超出部分才掉、下限 1 —— 与用户的描述一字不差。
教训写进 §5.4：**`grep -Context 0,10` 这种截断窗口不足以支撑"这个方法做什么"的结论**。

### ⭐ 待选奖励（`RewardsCmd.OfferCustom`）

* **`TestMode.IsOn` 分支必须跳过** —— 那是测试专用的固定奖励

* **循环里的份数**：`for (j = 0; j < intValue; j++) list.Add(new PotionReward(…))`
  只数"出现几次"会得到 1，实际是 N（大锅 5 瓶）。
  循环上界还常是局部变量，要跟着解析回 `DynamicVars`

## 5 · 工作原则

### 5.1 原始四条（保留原文，不改写）

1. **源码是机制的唯一真相**：`data/decompiled/sts2/` 里怎么写的，引擎就怎么实现。
   数值从 JSON 取，行为从 C# 取。
2. **每个机制配一个"对照测试"**：把源码里的常量/分支抄成断言。
3. **解析不了的必须上报**，不能静默丢弃。
4. **不做"近似就上"**：宁可标 `verified: false` 并排除出训练集，也不要让模型学错的机制。

### 5.2 ⭐ 铁律：一切机制以源码为准；**所有断言与猜测都必须经源码检验**

这是对第 1 条的**收紧**。原文"数值从 JSON 取，行为从 C# 取"留了一个口子：
数值也从 JSON 取。实测这个口子是错的 ——

* **社区库（codex）落后至少一个补丁**：逐字节对拍发现 651 个变量里 **37 个不一致（5.7%）**；
  v0.110.0 补丁说明证实"说明里的旧值 = codex，新值 = 源码"（Mangle 15(20)→20(26)、
  Biased Cognition 4(5)→5(6)、Relax 15(18)→16(18)、Crush Under 7→8、
  Terraforming 6→7、Refract 9→10）。
* 那 3 个无法判断来源的 API **不提供任何版本或日期**（没有 `Last-Modified`、没有 `ETag`，
  Cloudflare 只回 `Date`）—— 也就是说**没有任何办法确认它是不是最新的**。

所以现在收紧成：

> **数值与行为都从源码取。JSON 只提供 id、类名与结构（哪些字段存在），不提供任何数值。**

推导出的四条**可判定**要求：

| # | 要求 | 怎么算"做到了" |
|---|---|---|
| R1 | **每条机制声明必须带源码出处** | docstring / 注释里写出 `文件:方法名`。写不出来 = 还没验证，必须标出来 |
| R2 | **任何"看起来合理"的语义都不能直接采纳** | 先 grep 反编译源码确认；确认不了就不写进引擎 |
| R3 | **断言必须能追溯到源码行** | 测试 docstring 里写明依据；常量从源码抄，不从记忆抄 |
| R4 | **猜测必须显式标注且不得进训练集** | 进 `unverified_report()` / `verified: false`；报告里可见 |

补充两条边界：

* **社区文本只能用来"发现我可能漏了什么"，不能用来定值。** 它适合做对账（"codex 说这张卡
  有易伤，为什么我没抽出来？"），不适合做依据。
* **拿不准就停下来读源码。** 不要用"按常理应该是……"补上；下面那张表里的每一行都是这么踩出来的。

### 5.3 实测踩过的坑：每一次"合理猜测"都是静默错误

这张表是本条铁律的**实证**。每一行的共同点是：猜的那个语义看起来完全合理、
代码跑起来毫无异常、日志一切正常，而数值（有时是符号）是错的。

| 症状 | 当时的"合理猜测" | 源码事实 | 正确做法 |
|---|---|---|---|
| 提灯第 **2** 回合起每回合 +1 能量 | "`if (TurnNumber <= 1)` 是守卫，满足则不生效" | 数值钩子里 `if (…) return amount;` 是**排除式**；效果钩子里 `if (…) { 效果 }` 是**包含式** —— 同一个 `if` 两类含义相反 | `conditional_blocks()` 按条件后面跟的是 `return` 还是效果体判极性，极性一路带到求值层 |
| 弹珠袋**永远**不上易伤 | 同上（同一处根因） | 同上 | 同上 |
| 贤者之石只给**第一个**敌人加力量 | "`all_enemies` 就是 `enemy`，反正引擎按主目标结算" | `_apply_one` 对 `apply_power` / `damage` **有**全体分支（`_opponents_of`） | 删掉塌缩；`HittableEnemies`（集合）与 `cardPlay.Target`（单体）分桶 |
| 77 处变量值丢失（66 张卡） | "变量名从类型推，`parts[0]` 是数值" | 真机有两种写法：`new CardsVar(2)` 与 `new EnergyVar("GainEnergy", 1)` | 具名形式单独解析，并记 `named` 标记防止类型名被误当别名 |
| 面包（Bread）变成纯收益遗物 | "`ModifyMaxEnergy` 抽出来了，照着实现就是了" | 它的另一半在第 1 回合 `PlayerCmd.LoseEnergy(2)`，属于**同一个**遗物 | 有战斗阶段缺口的遗物，**数值半边一律不采纳** |
| 敌方格挡 4 回合从 15 涨到 60 | "格挡在玩家回合开始清，敌方那次是同一段逻辑" | `Creature.AfterTurnStart(side)` **双方阵营都清**，敌方那次发生在敌方回合开始 | 敌方阵营回合开始清敌方格挡（`burrowed` 例外） |
| `regen` 永远每回合回 5 点 | "回合结束回 N 点生命" | `Heal(Amount)` 后面紧跟着 `PowerCmd.Decrement(this)` —— 5 层总回复是 5+4+3+2+1 | 递减与治疗同一步；`plating` 同理（在回合开始递减，带两个豁免） |
| 测试断言"格挡不该被中毒消耗"却测了别的东西 | "跑完整个敌方回合再看格挡" | 敌方格挡在敌方回合开始就被清了，毒是之后才跳的 | 测试必须**只隔离被测的那一跳**，否则测的是另一条机制 |
| **12 张纯攻击卡打出去什么都不发生**（`Bludgeon` / `Clash` / `Flechettes`…） | "`DamageCmd.Attack(X)` 只是把意图里的数转成一次攻击，算装饰" | 怪物招式确实如此（数值来自意图），但**卡牌的伤害只有这一处出处** —— 于是 `DamageCmd.Attack` 的专用处理分支永远走不到（装饰判定在它之前），伤害整条消失且不报缺口 | 装饰判定按**调用方**分流：卡牌从源码抽伤害，怪物用 `damage_from_intent=True` 显式声明"数值来自意图" |
| **7 张攻击卡以"零效果"身份混进训练集**（`BodySlam`=伤害等于当前护甲） | "抽出了 `needs_runtime` 就算标记过了" | 抽取器把"量的字面量缺失"只写进了**统计表**（`var_without_literal::*`），没写进记录；`content` 那边又只在"文本版有效果"时才标残缺 | 量算不出来 = **硬缺口**：抽取器写进 `unsupported`，`content` 无条件标 `effects_incomplete`，另加结构护栏测试断言"可训练的牌不能零效果" |
| `Void`（抽到扣 1 能量）、`Disintegration`（上 6 层）、`WasteAway`、`MindRot`、`Sloth` 全都"什么都不做" | "这些是状态牌，本来就不做事" | 它们的效果写在**钩子**里（`AfterCardDrawn` / `OnChosen`），而抽取器只扫 `OnPlay` + 5 个 `TRIGGER_HOOKS`；没被扫到的钩子**连"未支持"都不报**。另外钩子里的 `unsupported` 只进了统计表没进记录 | 全扫 `override` 方法 + 钩子缺口进记录 + 报"未扫描的钩子：X"（`extract_cards.override_method_bodies`） |
| 关键字整批失效（`Ethereal` 不消耗、`Unplayable` 能打出、`Retain` 不保留） | "关键字只是卡面文字，行为另外有代码" | `CardKeyword.cs` 的枚举 doc 明写 "extra **automatic behaviors**"；七个关键字各有唯一执行点（见 `sts2_sim/keywords.py` 的表）。而文本库路径根本不带关键字，源码路径又因为"纯占位诅咒豁免"把关键字一起豁免掉了 | 关键字独立成层：与效果解耦（豁免只针对"是否算残缺"），每个关键字在 `core`/`runeffects` 里有实现 + 带出处的测试 |
| `Disintegration.OnChosen` 被判定"函数体里没有命令" | "用 `\w*Cmd\.\w+\s*\(` 扫命令就够了" | 真机大量写**泛型实参**：`PowerCmd.Apply<DisintegrationPower>(…)` —— 方法名后面紧跟的是 `<` 而不是 `(` | 命令识别式不要求紧跟 `(`（`COMMAND_CALL = \b(\w+Cmd)\.(\w+)`），泛型实参自己容忍 |

**结论**：这 9 条里有 7 条的根因是"没有回到源码确认语义"，而不是"实现写错了"。
所以规则不是"写完要对拍"，而是**写之前必须先读源码**。

### 5.4 每加一条机制，照这个流程走

```
1. 反编译源码里找到对应的类/方法（tools/extract_*.py 负责批量抽取）
2. 读**完整**方法体，不是只读签名 —— 极性、时机、豁免条件全在函数体里
3. 数值抄源码里的字面量 / DynamicVars，不抄社区文本、不抄记忆
4. 写进引擎，docstring 里标 `源码: 文件:方法名`
5. 配对照测试：把源码的常量/分支抄成断言，docstring 里写依据
6. 做**反向验证**：故意把实现改错，确认测试会失败（没有鉴别力的测试等于没有）
7. 抽不出来的部分进报告（engine_coverage() / relics_unresolved_numeric / …），不许静默
```

第 6 步最容易被跳过，也最值钱：本项目的"重开语义测试"就是靠反向验证
（故意重掷 → 轨迹必变）才证明了自己有鉴别力。

⚠️ **第 2 步的"完整"是字面意思**，连这个方法自己都要遵守。实测栽过一次：

```csharp
public static async Task GainMaxHp(Creature creature, decimal amount)
{
    if (amount < 0m) throw …;
    decimal num = await SetMaxHp(creature, (decimal)creature.MaxHp + amount);
    MapPointHistoryEntry entry = creature.Player?.RunState.CurrentMapPointHistoryEntry;
    if (entry != null) entry.GetEntry(...).MaxHpGained += (int)num;
    await Heal(creature, num);          // ← 会回血！在方法**最后一行**
}
```

当时用 `grep -Context 0,10` 只看到了前 10 行（到 `SetMaxHp` 为止），
就下了"加最大生命**不回血**"的结论，还把它写进了 docstring 当依据 ——
**是用户指出来的**。教训：**读方法体要用能覆盖整个方法的窗口**，
`-Context 0,10` 这种截断窗口不足以支撑"这个方法做什么"的结论。
修好之后 `GainMaxHp` 的语义是"加 N 上限 **+ 回 N 血**"，
`LoseMaxHp` 是"只砍血槽，当前血量超出新上限的部分才掉"（源码 `CreatureCmd.cs:841-882`）。

## 21 · 事件层：从 0/66 到"能跑的一小撮 + 每一张都有理由"

事件此前是**整块未做**（Run 层只有骨架期的两个占位事件 `bonfire` / `shrine`）。
这一节记录它怎么落地、现在能跑多少、剩下的每一个为什么不能跑。

### 21.1 真机模型（``MegaCrit.Sts2.Core.Models/EventModel.cs``）

```
BeginEvent(player, …)
  Rng = new Rng(runSeed + slot + XXH64(eventId))       ← 每个事件一条独立 RNG
  CalculateVars()                                       ← 把 DynamicVars 掷出来
  SetInitialEventState(…) → GenerateInitialOptions()     ← 第一页的选项
玩家点选项 → EventOption.Chosen()（EventOption.cs:174-185）
  同一个选项只结算一次（WasChosen 守卫）
  里面要么 SetEventFinished(desc)      结束
  要么   SetEventState(desc, options)   翻到下一页
```

所以"一个事件 = 一页页选项 + 每个选项的效果与去向"，这是一张**图**，不是一条链。

### 21.2 抽取（``tools/extract_events.py``）

复用卡牌那一套（`extract_effects` 的算子翻译、`parse_vars`、`method_spans`），
另外要处理事件特有的四种写法：

| 写法 | 处理 |
|---|---|
| `new EventOption(this, Plain, "…")` | 方法引用 → 跟到方法体 |
| `new EventOption(this, async delegate { … }, "…")` | 内联 lambda（**允许不带参数表**） |
| `new EventOption(this, () => SomeMethod(), "…")` | 表达式 lambda；**带参数**的（`RiderChosen(riders[0])`）如实报缺口 |
| `new EventOption(this, null, "…")` | **锁住的选项**（`IsLocked`）—— 正常内容，不是缺口 |

页与去向：第一页来自 `GenerateInitialOptions`，其余页来自
`SetEventState(L10NLookup("E.pages.X.description"), OptionsMethod())` ——
**页 id 从本地化 key 里取**，方法归属用 `method_spans` + `enclosing_method` 判。

### 21.3 引擎（``sts2_sim/events.py``）

* ``EventDef`` / ``EventPageDef`` / ``EventOptionDef`` / ``EventRun``：图 + 进行态；
* ``event_rng``：逐字复刻 `seed + slot + XXH64(id)`。为此实现了 **XXH64**
  （``sts2_sim/xxhash.py``），并用官方三个测试向量锁住
  （``xxh64("") == 0xEF46DB3751D8E999`` 等）—— 换成 `hashlib` 会得到**另一条**
  随机序列，数值对不上却不报错；
* ``parse_gate`` / ``gate_ok``：`IsAllowed` 的**白名单求值**；
* ``apply_option``：结算效果（走 `runeffects` 同一套算子）+ 翻页，带 `WasChosen` 守卫。

⚠️ 事件 RNG **没有**塞进 ``RngSet``：真机那 15 条是 run/玩家级的命名流，
而事件 RNG 是"每个事件临时开一条"（`EventModel.cs:133-138` 的注释明写
"we don't need to keep track of a given event's RNG state once it's over"）。
混进去会污染"分流结构"这条不变量。

### 21.4 三条诚实性规则

1. **条件算不出就不出现**。`IsAllowed` 只认白名单写法（act / floor / 金币 /
   生命 / 生命比例 / 药水数 / 牌组张数 / `&&` 组合 / `Players.Count == 1`），
   认不出的 → 事件排除出池子并进报告。判错的方向是"本不该出现的事件出现了"，
   比少一个事件严重。
   ⭐ 实测抓到一次**假放行**：`gate_of` 早先用 `balanced`（配平**圆括号**）
   取方法体，在第一个右括号处截断，于是 `crystal_sphere` 的条件
   `if (Gold >= 100) { return CurrentActIndex < 2; } …` 被截成
   `Gold >= 100` —— 看起来完全正常的"金币门槛"，实际漏掉了幕次条件。
   换成 `balanced_braces` 后它如实变成 unknown（并因此被排除）。
2. **有缺口的选项不静默降级**：选项效果里有引擎没有的命令、或需要玩家选牌 →
   **整个事件不可用**，而不是"少结算一半效果"。
3. **选项只结算一次**（`WasChosen`），锁住的选项不能点 —— mask 在动作空间里
   就不给，而不是"发出去再报错"。
