# 03 · 模型架构

## 3.1 总体形状：一个编码器 + 四个头

```
                                   ┌──► 战斗策略头   (自回归 + mask)
                                   │
Observation ──► Encoder ──► z ─────┼──► 战斗价值头   V_combat  (胜率 / 剩余HP / 回合数)
              (Entity TF)    │    │
                             │    ├──► Run 策略头    (三选一 / 地图 / 商店 / 事件)
                             └─► h (GRU) ──┴──► Run 价值头   V_run     (通关概率)

          共享的参数：卡牌 embedding 表、编码器、GRU
```

**为什么是一个网络而不是两个：** 战斗层和 Run 层的输入有 80% 重叠（牌组、遗物、HP、层数）。分成两个网络会重复学习这部分表征，而且 Run 层恰恰需要"这副牌能不能打赢接下来的精英"这种战斗知识。用一个共享编码器 + 两个任务头（用 task token 区分）最经济。

**为什么不是 LLM：** 真机桥接场景下每步几百毫秒的延迟不可接受；采样成本高 2–3 个数量级；而且无法用类型系统证明信息隔离（`docs/01` §1.3）。LLM 可以离线用于生成卡牌机制描述、初始化文本 embedding，但不做策略主体。

## 3.2 输入：Token 化方案

| Token 类型 | 数量 | 特征 | 位置编码 |
|---|---|---|---|
| **全局** | 1 | hp/maxHP（比例+绝对值双通道）、格挡、能量、金币、层数、act、难度、各牌堆张数、药水槽数、回合数 | — |
| **手牌** | ≤10 | `card_emb[id]` + 升级标志 + 当前实际费用 + 可打出标志 | ✅ 槽位位置 |
| **敌人** | ≤5 | `monster_emb[id]` + hp/maxHP + 格挡 + buff 向量（力量/敏捷/易伤/虚弱/中毒/…）+ **意图类型 emb** + 意图数值 + 意图次数 | ✅ 槽位位置 |
| **遗物** | ≤25 | `relic_emb[id]` + 计数器/充能数 | ❌ 无序集合 |
| **药水** | ≤3 | `potion_emb[id]` + 可用标志 | ✅ 槽位 |
| **历史事件** | ≤32 | 最近 K 步的动作类型 emb + 涉及的卡 id + 数值 | ✅ 时序 |
| **牌堆（抽/弃/消耗/整副）** | 0（池化） | 见下方"bag pooling" | — |

### bag pooling：牌堆不做 token

抽牌堆/弃牌堆/消耗堆/整副牌组都是**多重集**。用共享的卡牌 embedding 做加权池化：

```
pile_vec = MLP( Σ_{c} count(c) · card_emb[c] )        # 置换不变，天然无顺序
```

配一个 `count` 的幅度编码（`log1p(count)` 的小 MLP）让模型感知"有 3 张还是 1 张"。

**三个好处：**

1. **参数共享**：卡牌 embedding 表只有一份，手牌 token、牌堆池化、动作头输出全都用它。加新卡只需要加一行 embedding。
2. **`docs/01` 的牌序约束自动满足**——池化在数学上就不可能含顺序信息，不需要靠"写代码时小心"。这是本项目里少数几个"结构上不可能出错"的设计。

3. **紧凑**：4 个牌堆 × 300 张卡 = 1200 维 multi-hot 被压成 1 个 d 维向量。

> **待实测决定**：如果 StS2 的 UI 允许查看抽牌堆顺序（`docs/01` §1.8 问题 5），那么牌序属于 **L2 已揭示**信息，可以给。此时抽牌堆改为**有序 token 序列 + 位置编码**，作为消融实验的开关。
>
> **默认（保守）走池化版本。** 理由：池化迫使模型学"期望值"打法，泛化更好；而且"肯翻牌看顺序"与"记住牌序"是两种不同的能力，值得分开测量。

### 数值特征的处理

- 所有标量先裁剪到 `[-10, 10]` 再进 MLP（防爆值：力量叠到 999 的局是存在的）。
- HP 用**双通道**：`hp/max_hp`（比例，泛化）+ `log1p(hp)`（绝对值，判断"能不能扛住这一下"）。
- buff 层数用一个小向量，每类 buff 一维 + `log1p` 变换。
- 最终：`token = LayerNorm( emb[id] + Linear(continuous_features) + type_emb )`

## 3.3 编码器：Entity Transformer

```
Pre-LN Transformer × 4–6 层
  d_model = 256, heads = 8, FFN = 4d, dropout = 0.0–0.1
  token 数 ≈ 76（1 全局 + 10 手牌 + 5 敌人 + 25 遗物 + 3 药水 + 32 历史）
  输出：z = LayerNorm(global_token 的输出)
```

| 选择 | 理由 |
|---|---|
| Transformer 而非 MLP/CNN | 输入是**变长实体集合**，且存在实体间交互（哪张牌配哪个遗物、哪个敌人被上了易伤）。置换等变性是天然正确的归纳偏置 |
| 4–6 层足够 | token 数只有 ~76，交互深度浅（不需要 24 层那种长程依赖） |
| 不用稀疏注意力 | 序列太短，全注意力最省事 |
| 同类型内位置编码 | 手牌顺序人类看得见，有语义；敌人槽位顺序也稳定 |

### 可选升级：文本先验（对版本漂移最有价值）

卡牌/怪物/遗物都有一句机制文本（"造成 8 点伤害，施加 2 层易伤"）。用一个冻结的句向量模型或小型文本编码器把文本编成 `text_emb[id]`，与可学习的 `card_emb[id]` 相加。

**收益**：游戏 EA 阶段每周更新、新卡不断上线。有文本先验的模型对**没见过的卡**有 zero-shot 泛化能力；纯 ID embedding 遇到新卡只能当未登录词处理（全零向量），策略会退化。

**代价**：得多跑一个文本编码器（可离线预计算成表，推理时零开销）。建议 M3 阶段再加。

## 3.4 记忆：POMDP 的必需品

观测是部分可观的，"上回合敌人给我上了 2 层虚弱，所以这回合我应该先解掉"这类信息不在当前帧里。

| 层 | 结构 | 输入 | 重置时机 |
|---|---|---|---|
| 战斗 | GRU(d=256) | `[z_t, a_{t-1}, r_{t-1}]` | 战斗结束 |
| Run | GRU(d=128) | `[z_t, a_{t-1}, r_{t-1}]` | run 结束 |

**关键约束：GRU 的输入只能来自 `Observation` 与历史动作/奖励。** 任何隐藏状态混进去就等于绕过了整个信息隔离设计。CI 里对 `featurize.py` 做 import 白名单检查（见 `docs/01` §1.3 第二层）。

**待实验的决定**：战斗 GRU 是否在回合边界重置。
- 不重置（推荐）：能记住"上回合的虚弱还没消"。
- 重置：更短的信用分配路径，学得更快。

## 3.5 动作头：结构化 + 自回归 + mask

### 动作语法（环境与模型共用同一定义）

```
Action := PlayCard { card: HandSlot, target: Target }
        | UsePotion { potion: Slot, target: Target }
        | EndTurn

Target := Auto | Enemy(i) | AllEnemies | Self
```

### 因式分解

```
阶段 1:  p(kind)            over {play_card, use_potion, end_turn}   ← mask: 能量不足/无药水
阶段 2:  p(card | kind)     over 手牌槽位（或药水槽）                ← mask: 不可打出的牌
阶段 3:  p(target | card)   over 合法目标                            ← mask: 非单体牌此步 logprob=0

log π(a) = Σ 各阶段 log-prob          H[π] = Σ 各阶段 entropy
```

**为什么不用扁平动作空间**（`手牌 × 目标` 铺平）：
- 手牌数量每步都在变，扁平空间的语义会漂移。
- 因式分解让"选哪张牌"和"打谁"分开学，各自的数据效率都更高。
- 泛化：没见过的牌通过 embedding 相似度获得合理的初始概率。
- 与行为克隆数据对齐容易：人类日志天然就是 `(牌, 目标)` 结构。

### Run 层动作头（同一编码器，换 task token）

```
卡牌奖励:  p(pick | k 张候选)      k=3 或 4，含 skip/跳过
地图选路:  p(node | 合法相邻节点)   首行 ≤7（远古点的子节点）；之后 ≤3（列 ±1）
商店:      p(item | 货架) 或逐位二分类（买/不买，有预算约束）
营火/事件: p(option | 选项)
```

> 地图分支数按源码改过（见 `docs/12` 的"地图与三幕"一节）：真机的相邻关系是 `|Δcol| ≤ 1`
> （`StandardActMap.GenerateNextCoord`），所以**行进中**每个点最多 3 个后继；
> 但**第一步**是从远古点走向第一行的任意节点，最多 7 个。
> 旧文档写的"≤4"是骨架期近似网格的产物。

### 元动作头（SL 专用）

按 `docs/01` §1.4，SL 训练下还有一个与战斗策略并列的决策：**接受当前试次 / 重开**。

```
元策略:  p(restart | 可见状态, 已用重开次数, 试次历史编码)
       over { accept, restart }
```

- 输入需要额外编码**跨试次的知识**（"上一遍我看到第 3 回合会抽到 X"），建议做一个独立的 `attempt_encoder`：把历次试次的观测序列压缩成一个向量，与 `z` 拼接。
- **这条头不会从战斗策略里自动涌现**，必须显式训练（见 `docs/04` §4.5b）。
- 代价约束由环境强制（K 上限），网络不需要自己学"不能超过 K"。

### 战斗层的主方案：束搜索 + 价值评估

需要修正一个初版判断。侦察发现（`docs/07` §7.2 教训 3）：**"把战斗蒸馏进纯策略网络"有人失败了六次**；而 StS1 上用"回合内穷举手牌打法 + 40 个启发式权重"的**零神经网络**方案拿到了 52% 通关率。

回合内的动作空间其实很小（手牌 ≤10、目标 ≤5），因此战斗层的合理形态是：

```
策略网络  →  给出候选动作先验（剪枝，避免全排列爆炸）
束搜索    →  展开 actor 自己的决策树（宽度 B，深度 = 本回合出牌数）
V_combat  →  评估叶子节点（这是神经网络真正不可替代的地方）
```

**三个好处：**

1. 与"蒸馏失败"的教训一致——搜索保留的信息量远大于单次前向传播。
2. **束搜索只展开 actor 自己的决策，天然不涉及隐藏信息**，与 `docs/01` 的信息约束完美契合（唯一需要处理的是本回合内的随机效果，用 determinization 采样即可）。
3. 纯策略网络退化为**消融基线**，而不是主方案——这样"搜索到底带来多少收益"变成可测量的。

**代价**：推理算力 ×B。考虑到模型只有 ~10M 参数、单次前向 >50k/s，B=8–32 完全可承受。

### mask 是硬性要求

StS 的无效动作占比很高（能量不足的牌、非法目标、无药水时的操作）。不 mask 会让 RL 把大量样本浪费在"发现这步不能走"上，而且 PPO 的 log-prob 会被无效动作污染。**环境必须每步返回 `action_mask`。**

## 3.6 价值头与辅助任务

### 多任务价值头

| 头 | 输出 | 用途 |
|---|---|---|
| `V_combat` | 战斗胜率、结束时剩余 HP 比例、剩余回合数 | 战斗层 PPO 的 baseline + 一步前瞻的评估器 |
| `V_run` | 从当前局面出发的通关概率（或最终得分） | Run 层决策 + 地图选路 |

拆成多个标量比单个标量更有用：**"能赢但会掉 30 血"和"能赢且满血"在单标量价值下无法区分**，而后者才是精英/Boss 前的关键判断。

### 辅助预测任务（免费信号，强烈建议）

自我监督、不需要额外标注、显著加速早期表征学习：

| 辅助任务 | 预测目标 | 合法性 |
|---|---|---|
| 回合末敌方 HP | 本回合结束时各敌人剩余 HP | ✅ 预测未来 ≠ 读取未来 |
| 本场战斗末 HP | 战斗结束时的剩余 HP | ✅ |
| 下一抽的牌型分布 | 下一张抽到的牌的类型/费用分布 | ✅ 人类也在心里算这个 |
| 牌堆重建 | 从池化向量重建各牌堆的 bag | ✅ 帮助表征 |
| 意图预测 | 敌人**下一步**（已公开的意图之外）不预测 | ❌ 禁止 |

**权重 0.1–0.5**，与主损失联合优化。这几个辅助任务的价值极高：它们把"这个局面接下来会发生什么"的知识直接压进编码器，而 RL 的稀疏信号本来要花很久才能学到。

> 注意"预测未来"与"读取未来"的区别：让模型**猜**下一抽是什么，是合法且有用的（人类高手就在做这个）；让模型**知道**下一抽是什么，是作弊。前者是 `aux head + 监督标签`，后者是 `observation 里塞了 draw_pile[0]`。

### `V_combat` 的额外用途：束搜索的叶节点评估器

`V_combat` 不只是 PPO 的 baseline，它是 `docs/03` §3.5 束搜索的**叶节点评估函数**。这改变了它的训练要求：

- 精度要求更高（搜索对评估误差敏感：评估噪声会被搜索放大）
- **必须做 out-of-distribution 校验**——搜索会到达策略网络从未访问过的状态，`V` 在这些状态上的误差决定了搜索是帮忙还是帮倒忙
- 建议对 `V` 加一个"预测区间"或集成（多个 value head 取均值/方差），用方差做搜索的置信度

## 3.7 规模建议（单人 GPU 场景）

| 组件 | 尺寸 | 参数量 |
|---|---|---|
| Token embedding + 特征 MLP | d=256 | ~2M |
| Entity Transformer | 6 层 × d=256 × 8 头 | ~5M |
| GRU | 256 | ~0.5M |
| 策略头 + 价值头 + 辅助头 | 2 层 MLP | ~2M |
| **合计** | | **~10M** |

**吞吐预期**（RTX 4090 级别，粗略估计，需实测）：

- 推理：> 50k 决策/秒 → 支持大 batch 的向量化采样与一步前瞻
- 训练：5k–20k 决策/秒 → 战斗层 PPO 一天可处理 10⁸ 量级的决策

**先小后大**：从 d=128 / 3 层起步跑通全流程，再放大。StS 的观测 token 数不到 100，过大的模型只会拖慢迭代而不会提升胜率。

## 3.8 一些容易踩的坑

| 坑 | 后果 | 规避 |
|---|---|---|
| 卡牌 embedding 只用于手牌，牌堆用 one-hot | 参数翻倍且不共享，加新卡要改两处 | 全项目**一张**卡牌 embedding 表 |
| 给池化向量加位置编码 | 顺序泄漏（违反 `docs/01`） | 池化路径不接位置编码 |
| 敌人意图不进输入 | 模型学不会"该防御了"，胜率断崖 | 意图是公开信息，必须给 |
| 历史 token 无限增长 | 显存爆、性能崩 | 固定窗口 32，或换 GRU 记忆 |
| 动作空间两侧定义漂移 | Rust 环境与 Python 模型对不上，静默错位 | 用 Rust 生成 Python 侧枚举，加一致性测试 |
| 训练时把 seed 当特征 | 模型记忆种子，评估虚高 | `docs/01` §1.3 第四层 |
