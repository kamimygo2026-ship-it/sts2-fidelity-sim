# 07 · 已有实现盘点与复用决策

> 由技术侦察得出（证据链见 §7.6）。**结论：不从头写模拟器。**

## 7.1 关键发现：有人已经做过一遍，并且卡在同一个地方

`zhiyue/sts2-rl-agent`（62★，Python+C#，2026-03 创建）几乎就是我们原计划的 M0–M3：

| 项 | 他们的结果 |
|---|---|
| 模拟器 | 纯 Python 重实现，参照反编译的 C# 源码审计 |
| 吞吐 | ~1,200 场战斗/秒，~28,000 步/秒 |
| 观测 | **131 维扁平 float32 向量** |
| 动作 | `Discrete(61)`（战斗）/ `Discrete(100)`（全局 run） |
| 算法 | MaskablePPO（sb3-contrib） |
| **战斗胜率** | **~92%**（Act 1 Ironclad） |
| **全局通关率** | **0%——训练 100 万步之后仍然是 0%** |
| 预训练模型 | 未发布（releases 为空） |

他们自己的 known issues：`"The full-run environment produces 0% win rate even after 1M training steps."`、`"exact parity is still broader than the currently audited test surface"`。

**这是一份极其宝贵的免费实验报告。** 它同时验证和否证了本规划中的若干判断：

| 判断 | 是否被验证 |
|---|---|
| 战斗层可以独立训好（信号密） | ✅ 92% |
| 端到端全流程 RL 会因稀疏奖励而失败 | ✅ 0% |
| 扁平观测向量泛化差 | ✅ 疑似主因 |
| 扁平动作空间（`Discrete(61)`）不够 | ✅ 疑似主因 |
| 需要分层（战斗层 → Run 层） | ✅ 本项目 `docs/04` 的核心主张 |
| 需要课程学习（连续战斗，HP 是跨战斗资源） | ✅ 本项目 `docs/04` §4.3 第 5 级 |

> **他们失败的两个技术选择（扁平观测 + 扁平动作）正是 `docs/03` 明确反对的。** 这不是巧合——`docs/03` 的 entity transformer + 因式分解动作头就是为了解决这两个问题而设计的。

## 7.2 三个必须吸收的教训

### 教训 1：战斗能学会，全局玩不通
→ 印证分层与课程。**不要在 M3 之前碰端到端全流程。**

### 教训 2：扁平表示会杀死泛化
131 维扁平向量无法表达"这张牌和这个遗物的组合"，`Discrete(61)` 无法在牌堆大小变化时保持语义。
→ 坚持 `docs/03` 的实体化 token 编码 + 自回归因式分解动作头。

### 教训 3：有人"把战斗蒸馏进网络"失败了六次
`Jialeiv/sts-rl-agent` 的报告里写着 `"six honest negative results on distilling combat into networks"`（同时他们用学到的非战斗策略比 MCTS bot 多打 11 层）。

同时，StS1 的 `xaved88/bottled_ai`——**完全没有神经网络**——用"回合内把手牌的所有打法穷举一遍（图遍历 + 自建模拟），再用约 40 个启发式权重挑最好的结果"，在观者上拿到 **52% 通关率**。

→ **这提示战斗层的正确形态可能不是"纯策略网络"，而是"搜索 + 评估函数"**：
- 回合内的动作空间（手牌 ≤10、目标 ≤5）其实小到可以 beam search
- 神经网络的真正价值在于**状态评估函数**（`V_combat`）和 **Run 层**
- 这也解释了为什么"蒸馏进网络"屡屡失败——把一个搜索问题硬压成单次前向传播，会丢掉大量信息

**对 `docs/03`/`docs/04` 的修订建议**（已反映）：战斗层主方案改为 **"策略先验 + 束搜索 + 价值网络"**，纯策略网络作为消融基线而不是主方案。这个方向还有一个额外好处：**束搜索只展开 actor 自己的决策，天然不涉及隐藏信息**，与 `docs/01` 的信息约束完美契合。

## 7.3 复用决策

**结论：模拟器不从头写，只重写接口层。**

| 模块 | 决策 | 对象 |
|---|---|---|
| **规则引擎** | 评估后复用其一 | `Akirakato1/Slay-the-Spire-2-Simulator`（Rust，5★，MIT）、`yizhang-dream/sts2-simulator`（Python + gymnasium + **behavior-parity tests** + 真机 TCP bridge）、`zhiyue/sts2-rl-agent`（最完整但接口设计错误） |
| **观测/动作接口** | **必须重写** | 现有实现的接口按 §7.2 教训 2 是错的；规则实现可复用，接口不可 |
| **内容数据** | 复用 | `spire-codex`：`GET /api/exports/{lang}` 可下全量 ZIP，无需 key，60 req/min/IP |
| **真机桥接** | 复用 | `Gennadiyev/STS2MCP`：localhost REST，双向读写，含**注入动作**能力 |
| **对拍数据** | 复用 | STS2MCP 读状态 + 人工录制；`yizhang-dream` 的 parity tests 可参考 |

工程量因此从"写一个完整游戏"降到"**写观测/动作接口 + 训练管线 + 验证**"——省掉了最大的一块。

### 评估顺序（M0 的第一件事）

```
1. 逐个 clone（你在本地做，我这边无出网）
2. 跑它们的自带测试，看能不能跑通、覆盖多少内容
3. 用我们的真机对拍脚本打它们的行为一致性
4. 选保真度最高的那个，作为规则引擎基座
5. 在其上重写 observe() / action 定义（docs/02 §2.8、docs/03 §3.5）
```

**验收标准**：选中的引擎能通过我们 10–20 局真机对拍中的 ≥90%，否则退回自建（`docs/02` 的 MVP 边界）。

## 7.5 StS1 的方法论标杆

| 项目 | 价值 |
|---|---|
| `gamerpuppy/sts_lightspeed`（C++17，96★，MIT） | **真机数值对齐的标杆**：`"Designed to be 100% RNG accurate"`，`1M random playouts in 5s with 16 threads`。完成度：全敌人 + 全遗物 + 全 Ironclad 牌 + 无色牌 + 战斗外全部。**注意它自己还没做到"不知 RNG 状态的树搜索"**——正好是我们的核心命题 |
| `ForgottenArbiter/CommunicationMod`（Java，153★，MIT）+ `spirecomm`（Python，102★，MIT） | 真机控制协议的事实标准，README 直接写 `"providing a protocol for allowing another process to control the game"`。STS2MCP 是它在 StS2 上的对应物 |
| `xaved88/bottled_ai` | **非神经网络强基线**：观者 52% 通关率，回合内穷举 + 40 个启发式权重。见 §7.2 教训 3 |
| `XlousMao/STS-AI-Master`（7★，MIT） | StS1 上的 PPO + 多实例 headless 采集，但仍在 Stage 2，无胜率发表 |

> `sts_lightspeed` 的 README 里那句 `"Tree Search (best result, knowing the state of the game's rng)"` 值得注意：**连这个领域的标杆项目，树搜索都还是"知道 RNG 状态"的版本**。我们要求的"不知道 RNG 状态"（`docs/01` §1.4 的信息集搜索）是一个**没人做完的开放问题**。这既是难点，也是这个项目的价值所在。
