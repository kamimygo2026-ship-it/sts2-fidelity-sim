### 7.2 静默变强嫌疑（**已实现**的能力，需逐条回源码确认）

引擎的 `damage_additive` / `block_additive` 是**开关**（无条件加层数），而真机的 `ModifyDamageAdditive` / `ModifyBlockAdditive` 几乎都带谓词：

```csharp
if (base.Owner != dealer) return 0m;       // 只有自己的伤害
if (!props.IsPoweredAttack()) return 0m;   // 只有「吃力量」的攻击
if (!card.Tags.Contains(CardTag.Shiv)) return 0m;
```

用开关表达带条件的源码 = **丢掉条件 = 能力变强**，症状只是「伤害高几点」，没有报错。工具报的是**线索**；下面每条都已回源码与引擎逐条核实。

| 能力 | 源码成员 | 核实结论 |
|---|---|---|
| `strength` | `StrengthPower.ModifyDamageAdditive` | 已核实：结构上成立 |
| `dexterity` | `DexterityPower.ModifyBlockAdditive` | 已核实：结构上成立 |
| `vigor` | `VigorPower.ModifyDamageAdditive` | 已核实：残余简化（顺序执行下等价） |

* `strength` —— `compute_damage` 全仓库只有**一个**调用点（`deal_damage`，core.py:725），而 `unpowered=True` 的分支在它之**前**就返回（core.py:722）—— 所以「`props.IsPoweredAttack()`」这一条由调用路径保证；「`base.Owner != dealer`」由 `attacker.power(pid)` 按**经手者**查表保证。
* `dexterity` —— `gain_block` 里 `unpowered=True` 直接跳过 `compute_block`（core.py:607-609），对应源码的 `props.IsPoweredCardOrMonsterMoveBlock()`；「按拥有者查表」对应 `cardSource.Owner == base.Owner`。
* `vigor` —— 源码还把加成**绑定到下一条命令/同一张牌**（`internalData.commandToModify` 两处判断），引擎的语义是「下一次吃力量的攻击 +层数、用后移除」。单体顺序执行下两者结果相同，**但引擎没有对应用例**，也没有实现那种绑定。

**仍未回答的问题**（下一批要做成用例）：

* 「powered 但**不是攻击**」的伤害/格挡在真机里存在吗？若存在（例如某张技能牌造成非 Unpowered 伤害），它现在会吃到力量 —— 需要一条**反例用例**把这条边界钉住。
* 怪物招式的格挡走的是 `IsPoweredCardOrMonsterMoveBlock()`，引擎目前只按 `unpowered` 标志区分；怪物的非 Unpowered 格挡是否吃玩家敏捷需要确认。


## 8. 共性分析

1. **卡牌缺口集中在前 4 族**：`动态数值公式（`CalculatedVar` / `DynamicVars` 组合）` 等 4 族共 121 张，占未纳入卡牌的 55%。剩下十几族是长尾，多数是各自只有一张卡用的冷门命令。
2. **能力缺口是卡牌缺口的根**：24 处准入拒绝是「施加了引擎没有的能力」，而能力那一侧只有 26 个待实现、且前三族就占 18 个 —— **补一个钩子位往往整族落地**，不是 170 份独立工作。
3. **跨内容类型共享同一批机制原语**（数字由本次扫描算出）：

| 机制原语 | 卡住哪些内容 |
|---|---|
| **选牌动作**（从候选里挑 N 张，含生成物选牌） | 卡牌 10 张 + 药水 6 处 + 事件附魔族 19 条 + 部分遗物 |
| **动态数值公式**（`CalculatedVar` / `WithHitCount` / 变量组合） | 卡牌 39 张 |
| **生成物落位**（入手 / 入抽牌堆 / 自动打出 / 召唤） | 卡牌 23 张，药水若干 |
| **附魔系统** | 事件 19 条原因（选牌用途 `enchant` 与附魔语义） |
| **手牌 / 时点触发器** | 卡牌 6 张（`on_turn_end_in_hand` 等） |
| **事件内战斗交接 + 执行帧栈** | 事件 5 条，且是嵌套选择 / 自动打牌的共同前置 |
| **遗物条件建模**（取模计数 / 随机目标 / 卡牌标签） | 遗物 277 处缺口里的多数 |
| **解锁状态与修正器**（`UnlockState` / `Modifier`） | 跨全部内容类型，目前一律当「未解锁 = 排除」 |

4. **遗物缺口不是均匀分布的**：时机上 `AfterObtained` 一处就占 34 处（一次性获得型效果），而类别上 `commands` 140 处 > `query` 87 处 > `bookkeeping` 47 处 —— 说明一半以上是「钩子位有了但不会执行那条命令」，而不是「没有这个时机」。
5. **三类性质必须分开看**：

   * **缺机制原语**（一次实现解锁一批）：上面的表 —— 这是主线，也是唯一值得投入架构的。
   * **缺内容体量**（机械劳动、风险低）：26 个能力、19 瓶药水、198 个遗物 —— 逐条照源码填即可，但要按「能力 → 卡牌」的顺序做，否则填完能力才发现卡还卡在别处。
   * **不该做**（应当明确排除）：表现层与多人（`Layout.*` / `SetPortrait` / `HoverTip`）、废弃内容（`Deprecated*`）、任务系统（`PlayerCmd.CompleteQuest`）。本次扫描识别出：卡牌 1 张、药水 0 瓶、遗物 1 个、恒假/废弃事件 7 个。排除它们不需要理由，保留它们只会让缺口数字虚高。
