# 11 · 架构对照：模拟器 vs 真机

> 问题：**我的结构跟源码像不像？不像的地方有没有风险？**
>
> 做法是逐层对照，每一层标"对齐程度"，并把**已经因此踩到的坑**写进去 ——
> 结构差异本身不是问题，"差异带来的静默错误"才是。

配套工具：`python tools/architecture_audit.py`（可重复跑，数字都是实测的）。

## 11.1 总览

下表数字全部来自 `python tools/architecture_audit.py`（现场实测，不是抄的）。

| 层 | 真机 | 我的 | 对齐 |
|---|---|---|---|
| **模型层** | 一个对象一个类（Cards 596 / Relics 300 / Powers 268 / Monsters 121 / Potions 65 / Orbs 5） | 一张内容表 + 一个处理器（597 / 299 / 267 / 115 / 65 / 5） | ✅ 数量对齐（差 +1 / −1 / −1 / −6 / 0 / 0，需逐条核） |
| **命令层** | `Commands` 目录 20 个 Cmd 类 | **18 个算子**的表 | ⚠️ 语义等价，粒度更粗 |
| **钩子层** | `AbstractModel` 185 个虚方法 + `Hook.cs` 148 个静态入口 | **20 个事件钩子 + 11 个查询接口** | ❌ **差距最大的一层**（见 11.2） |
| **伤害管线** | `Hook.ModifyDamageInternal`：加法 → 乘法 → 钳制 → 单次截断 | 同顺序、同舍入（乘法表驱动） | ✅ 逐句照抄，但**无真机对拍** |
| **出招状态机** | `MonsterMoveStateMachine` | `monster_ai.py` 539 行，覆盖 115/115 只怪 | ✅ 忠实翻译（不是近似）；运行时条件仍需逐条用例 |
| **回合时序** | `CombatManager.StartTurn` + `SetupPlayerTurn` | `core.start_player_turn` | ✅ 逐步对齐（引用行号写在 docstring） |
| **地图** | `StandardActMap`：7 列、路径生成、点类型配额、`MapPathPruning`、`MapPostProcessing` | `mapgen.py` 873 行，**4 张幕地图 / 3 个幕索引** | ✅ 算法与判定逐条复刻；PRNG 不同，**不是同种子一致** |
| **幕与房间序列** | `ActModel.GenerateRooms`：弱怪/普通怪/精英队列 + 标签去重 + 抓包重复装填 | 逐节点从全局遭遇池抽 | ❌ 未接（见 `docs/13` §16+） |
| **RNG** | `RunRngType`(12) + `PlayerRngType`(3) | `STREAMS` 15 条 + `act_selection` / `act_{n}_map` 两条按用途另起的派生流 | ✅ 两层、逐条对应（**底层 PRNG 不同**） |
| **信息边界** | 玩家看不到的就不该进观测 | `Hidden` / `RunHidden` 容器 + AST 门禁 + 反作弊测试 | ✅ 这是本项目的独有要求，真机没有对应物 |

## 11.2 钩子面：185 vs 20，但要拆开看

直接把 185 当成"我缺 165 个钩子"是错的。真机那 185 个虚方法里：

| 类别 | 数量 | 模拟器需要吗 |
|---|---|---|
| 事件 / 修正型（`AfterDamageReceived`、`ModifyBlockMultiplicative`…） | **128** | ✅ 需要，**这是我真正的缺口** |
| 排序变体（`AfterCardPlayedLate`、`BeforeCombatStartLate`…） | 27 | ⚠️ 大部分是动画时序，无头模拟器可以合并；但**顺序本身**要保住 |
| 查询 / 决策型（`ShouldPlay`、`ShouldClearBlock`、`ShouldDraw`…） | 27 | ✅ 需要，我已实现 11 个 |
| 其它（UI / 多人） | 1 | ❌ 不需要 |

所以诚实的说法是：**事件型钩子覆盖 20/185 ≈ 10.8%，查询型 11/27 ≈ 41%。**

这个差距不是"偷懒"造成的，而是**按需实现**：我只实现"已经抽取出来的机制"需要的钩子。
代价是——**每加一个新机制，可能同时要加钩子位和调用点**，而"忘了加"是静默的。

## 11.3 ⭐ 结构性风险：硬编码调用点

这是本次审计最重要的发现。

真机的钩子是**一个入口分发给所有模型**：

```csharp
// 任意位置
await Hook.AfterDeath(runState, creature, …);
// Hook.cs 内部遍历所有 model，谁重写了就调谁
foreach (var model in runState.IterateAllModels()) await model.AfterDeath(…);
```

我的钩子是**在每个需要的地方手写调用**：

```python
# core.py 里十几处
power_rules.on_attacked(defender, attacker, state, events, …)
power_rules.on_card_played(state, events, definition.card_type, card)
```

差别在于：真机漏调用是**不可能**的（只有一处）；我漏调用是**很容易**的，
而且症状是"该发生的事没发生"，日志一切正常。

### 已经因此踩到的坑：4 条死亡路径

审计时发现 `core.py` 里有 **3 处直接把 `hp = 0`**，全都绕过了死亡钩子：

| 路径 | 漏掉的后果 |
|---|---|
| 末日处决（`dies_to_doom`） | `crab_rage` 不暴怒、`stock` 不补人 |
| 招式自爆（`kills_self`） | `surprise` 不召唤、`minion` 不连锁 |
| 中毒 / 掉血（`deal_raw_damage`） | 连 `AfterDamageReceived` 整条都不跑 —— `slippery` **永不递减** |

也就是说：**滑溜的墨宝会变成一个永久免伤**（每次最多掉 1 点且永不减层），
而所有单元测试都是绿的。

### 修法：集中成唯一入口

新增 `core.mark_dead()` —— 对应真机的 `CreatureCmd.Kill`，是**唯一**的死亡入口。
所有路径（伤害致死 / 末日 / 自爆 / 中毒）都经过它，钩子只在这里触发一次。

⚠️ 修的时候又踩了一个：判"是否已处理过"**不能**看 `hp > 0` ——
伤害路径是**先扣血再调用**，进来时 hp 已经是 0 了。用血量判断会让
"所有由伤害造成的死亡"都不触发钩子（而末日那条路径却正常，
这种"一半对一半错"最难猜）。改用显式标志 `death_processed`。

`tests/test_death_paths.py`（6 个测试）盯住这件事，其中一条是**结构护栏**：
扫描 `core.py`，发现裸的 `hp = 0` 就失败 —— 防止有人又加一条绕过钩子的路径。

### 同类风险的其它实例

同一个根因（钩子调用点分散）在本项目里反复出现，都是同一个形状：

| 症状 | 根因 |
|---|---|
| 手牌触发器里的燃烧打的是敌人 | `_apply_one` 的 `damage` 分支没看 `eff.target` |
| 敌人格挡无限累积 | 敌方回合忘了清格挡（真机在 `CreatureAfterTurnStart` 里） |
| `regen` 永远回血 | 少了 `PowerCmd.Decrement` 那一步 |
| 招式改了效果来源后敌人不再攻击 | `_effective_effects` 只在已有 `damage` 效果时才覆盖数值 |
| 苦痛能力全部不触发 | 钩子只遍历了敌人，而这些 debuff 挂在**玩家**身上 |

## 11.4 我"抄对"的几处

不是所有层都需要改。下面这几层是**结构级对齐**，改源码时能直接跟着改：

1. **伤害管线**（`compute_damage`）：加法 → 乘法 → 钳制 → 单次截断，
   全程 `Decimal`，中间不取整。docstring 里写了"逐次截断会差 1 点"的实例。
   乘法阶段现在是**表驱动**（`DAMAGE_MULTIPLIERS`），与真机"每个 Power 各写一个
   `ModifyDamageMultiplicative`"是同一套语义。
2. **出招状态机**（`monster_ai.py`）：`roll_move` / `FollowUpState` /
   `AddBranch` 的重复约束 / `ConditionalBranchState` / `MustPerformOnceBeforeTransitioning`
   全都是按 `MonsterMoveStateMachine` 翻的，**不是**"大致等价"。
3. **回合时序**：`start_player_turn` 的每一步都对着
   `CombatManager.cs:688-927` 的注释写，包括"玩家第 1 回合不清格挡"这种细节。
4. **`ValueProp`**：`Unpowered` / `Unblockable` / `Move` 三个标志的语义与传播路径
   与 `ValuePropExtensions.cs` 一致（`IsPoweredAttack()` = 有 `Move` 且非 `Unpowered`）。

## 11.5 ✅ 已落地的结构接口：钩子总线（sts2_sim/hooks.py）

审计结论里最值得做的一件事，已经做了。

### 是什么

把"什么时机、谁触发、在哪调用"集中成**一张声明表**：

```python
HOOKS["on_attacked"] = HookSpec(
    name="on_attacked",
    source="Hook.AfterDamageReceived",     # 真机出处（铁律 R1）
    scope="owner",                          # 遍历谁
    timing="受到伤害之后（扣血已完成）",      # 人类可读的时机
    call_sites=("deal_damage", "deal_raw_damage"),   # 在哪调用
    args=("attacker", "unblocked", "from_card", "powered"),
)
```

`hooks.fire("on_attacked", state, events, dispatcher, ...)` 是**唯一**的触发入口。

### 它挡住了什么

| 以前 | 现在 |
|---|---|
| 钩子名拼错 → 安静地什么都不做 | **立刻 `KeyError`** |
| 漏传实参 → 对应能力永不触发，没有症状 | 声明里写了 `args`，少传**立刻 `TypeError`** |
| 遍历范围写错（只遍历敌人、漏了玩家）→ 苦痛族全不触发 | 范围在声明里写死，`scope="both"` 是显式的 |
| "哪些路径会触发这个钩子"散在 core.py 各处 | `call_sites` 声明 + 测试校验函数真实存在 |
| 没法回答"这一跳到底跑了哪些钩子" | `with hooks.trace() as r:` → 可断言的分发/响应记录 |

### 遗物也上了同一条总线

遗物与能力重写的是**同一批** `AbstractModel` 虚方法，所以它们理应在同一张表上：

```python
RELIC_TIMING_TO_HOOK = {
    "combat_start":           "relic_combat_start",
    "before_side_turn_start": "relic_before_side_turn_start",
    "after_energy_reset":     "relic_energy_reset",
    "after_player_turn_start":"relic_after_player_turn_start",
    "after_side_turn_start":  "relic_side_turn_start",
}
```

`core.py` 里的 5 处遗物调用已经改成 `hooks.fire("relic_*", …)`，
与能力的钩子走同一条路径。`hooks.audit()` 会检查三个方向的一致性：
能力钩子位 ↔ 总线声明、遗物时机 ↔ 总线声明、每条声明本身的完整性。

### 轨迹的两种语义

调试时两者都要，它们回答不同的问题：

* **分发过**（`names()` / `count()`）—— "核心流程走到这个时机了吗"。测的是**流程**。
* **有人响应**（`responders()` / `count_responded()`）—— "这个能力真的被触发了吗"。测的是**能力**。

只记响应者会让"流程有没有走到"没法断言（测试里的怪常常没有能力）；
只记分发则看不出"到底谁响应了"。

### 新增的护栏（`tests/test_hook_bus.py`，14 个测试）

* 声明与 `PowerRules` 钩子位一一对应（`hooks.audit()`）
* 每条声明都带源码出处与触发时机
* **声明里写的调用点必须真实存在** —— 重构改了函数名而没改声明会失败
* 未声明的钩子名 / 缺实参 → 必须报错
* 一个回合分发到全部四个回合级遗物时机
* 轨迹能区分"分发"与"响应"

## 11.6 结论

* **数据层完全对齐**：每一类内容都是"按对象的类抽出来的一条记录"，数量对得上。
* **机制层是"逐条搬运"而不是"结构同构"** —— 这是有意的取舍：
  真机的 185 个虚方法里有一半是动画/多人/UI，照搬没有意义。
* **地图层已从"近似网格"换成"逐条复刻"**（`StandardActMap` + `MapPathPruning` +
  `MapPostProcessing`），但**幕级房间序列**（`ActModel.GenerateRooms`）还没接 ——
  两者合起来才算"整局生成对齐"。
* **真正的风险集中在"钩子调用点分散"**：不是"实现错了"，而是"某个路径忘了通知"。
  已经踩到 4 条死亡路径 + 5 个同类实例。
* **缓解手段（已经落地）**：
  1. 关键流程集中成唯一入口（`mark_dead` / `_sync_player_from_combat` / `_roll_unknown_room`）
  2. 结构护栏测试（扫描裸 `hp = 0`）
  3. 台账测试（缺口数不许悄悄变大）
  4. 反向验证（故意改错，确认测试会失败）

**下一步建议**：钩子总线已经能回答"哪些路径会触发哪些钩子"
（`HookSpec.call_sites` + `hooks.audit()`），所以剩下的不是"再建一层结构"，
而是**按内容批次补事件型钩子的缺口**：每批内容开工前先看 `hooks.audit()` 报出的
缺口，补完再放行对应卡牌/遗物 —— 顺序反了就会得到"遗物在、效果不在"的静默失效。
